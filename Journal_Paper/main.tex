\begin{abstract}
The SQL standard introduced the \texttt{MATCH\_RECOGNIZE} operator in 2016 to support row pattern recognition, enabling the detection of ordered sequences of rows in a table that match a user-defined pattern. This capability is useful in diverse domains—for example, a financial institution may detect a sequence of small deposits followed by rapid transfers and large withdrawals, a known indicator of potential money laundering, or climate analysts may identify heatwaves as three or more consecutive days with maximum temperatures exceeding 40°C.
\texttt{MATCH\_RECOGNIZE} is now supported by several leading database systems, such as Oracle, Snowflake, and Flink. In this paper, we present a prototype that brings this functionality to Pandas DataFrames, a widely used in-memory data structure in the Python data science ecosystem. Our prototype parses SQL-based pattern queries that execute
\texttt{MATCH\_RECOGNIZE()} queries directly from an SQL string on a \texttt{pandas} DataFrame. The system supports SQL:2016 row pattern recognition (RPR) semantics, including \texttt{PARTITION BY}, \texttt{ORDER BY}, \texttt{PATTERN}, \texttt{DEFINE}, and \texttt{MEASURES} for offline analytics in Python. It constructs an abstract syntax tree (AST), compiles patterns into non-deterministic finite automata (NFA), and executes them efficiently over DataFrames. We evaluate the engine against Trino~473 and Oracle~21c EE on the Amazon UK
Products dataset, running five pattern families over six sizes up to 2,222,742
rows. The three systems return identical results in all 30 pattern--size cells,
and the engine averages 0.17 seconds per cell against 1.04 for Oracle and 1.98
for Trino. A scalability test on the Amazon Reviews 2023 corpus extends the
input to 227,899,533 rows, which the engine completes on every pattern family.
The declarative form also reduces code size compared to native Pandas
implementations, extending the convenience of SQL pattern matching to Python
users while preserving correctness equivalent to that of established SQL
engines.
\end{abstract}

\section{Introduction}
Pattern matching is the process of analyzing a sequence of data points, which can be rows in a table or events in a stream. Pattern matching plays a crucial role in data analysis, especially for identifying patterns and shapes or specific sequences of events or behaviors in areas like identifying chains of transactions related to money laundering in finance\cite{10.5120/ijca2022922446}, revealing fraudulent behaviours of users in security logs\cite{zemke2007pattern}. Patterns in data can be described using regular-expression-like syntax, like those commonly used in textual analysis. However, unlike traditional text-based regular expressions, these patterns are applied at the row level, enabling analysts to match and extract meaningful sequences across entire records rather than individual characters.

The \texttt{MATCH\_RECOGNIZE} (MR) clause was introduced in the SQL:2016 standard \cite{iso2016,ISO2021}, enabling users to define and search for patterns within ordered sequences of rows directly in SQL queries.
The {MATCH\_RECOGNIZE} SQL clause enables advanced pattern-based querying over data tables. Although it was standardized in SQL:2016 \cite{iso2016,ISO2021}, a few DBMS support it. For example, among well-known traditional RDBMSs, only Oracle\cite{oracle2022,book} supports the MR operator. In the big data analytics systems, Trino~\cite {trino2022,trino2021row}, Snowflake~\cite{snowflake2025match_recognize}, and Apache Flink~\cite{flink} support the MR operator.
Cloud warehouses have since followed: BigQuery documents the
clause~\cite{bigquery2025matchrecognize}, and Databricks introduced beta
support in Runtime~19.0~\cite{databricks2026matchrecognize}. By contrast,
PostgreSQL~18 still lists the related SQL features as
unsupported~\cite{postgresql18unsupported}, while DuckDB lists native
\texttt{MATCH\_RECOGNIZE} as planned work~\cite{duckdb2026roadmap}. 

% and it was supported in several modern databases like Trino  and Oracle , this feature is missing from the Python data science landscape. In this paper, we address this gap by bringing \texttt{MATCH\_RECOGNIZE} support to Pandas.

Without the support for the declarative MR clause, tasks requiring detecting multi-row patterns often require complicated combinations of SQL window functions, self-joins, or even procedural extensions and user-defined functions to loop through rows and maybe add some external programming outside the database~\cite{findling2025bringing}. As soon as the pattern grew beyond two or three steps, the SQL statement expanded into multiple lines full of row-number calculations, timestamp comparisons, and complex JOIN conditions. Not only is the code hard to write and even harder to maintain, but each extra join or analytic window often means an extra table scan, leading to poor performance. In practice, many teams either accepted these limitations or abandoned SQL for external scripts and ETL pipelines just to get reliable pattern matching SQL expanded into multiple lines~\cite{cao2012optimizationanalyticwindowfunctions}.

With the introduction of MATCH\_RECOGNIZE in the SQL:2016 standard, rather than a multitude of lines of code and using window functions and self-joins, Instead, a single declarative MATCH\_RECOGNIZE statement that clearly defines the data partitions, ordering, pattern, and output measures. Simplifying both the syntax and readability of pattern-matching queries, MATCH\_RECOGNIZE clause enables users to organize their data into logical groups using \texttt{PARTITION BY}, specify the sequence of row analysis using  \texttt{ORDER BY}, and define the actual pattern using the \texttt{PATTERN} section, which uses regular expression-like syntax. Logical conditions that define each pattern element are clearly stated in the \texttt{DEFINE} clause, while the \texttt{MEASURES} clause determines what information is extracted from each detected match. This structure allows complex sequence patterns to be described clearly and concisely. It ensures that detecting, classifying, and summarizing sequences can be performed efficiently and consistently within standard SQL queries, such as trends, repeated behaviors, or sudden changes, directly within standard SQL queries \cite{michels2018new}.

Before introducing the MATCH\_RECOGNIZE method in Pandas, detecting multi-row patterns such as consecutive upward trends, cyclical oscillations, or conditional event sequences required manual integration of multiple low-level operations. A typical workflow involved creating multiple shifted versions of each column (df['value'].shift(-1), shift(-2), etc.), building complex boolean masks, filtering or using groupby().apply() to stitch subsequences back together, and then pivoting or renaming columns to get the desired output. This approach was verbose (often 10+ lines for modest patterns), prone to off-by-one or alignment bugs, and hard to extend to longer or conditional patterns.

For example, an e-commerce platform that tracks all customer purchases: the marketing team wants to find customers who are decreasing their spending money by buying progressively cheaper items in three consecutive purchases, by detecting three consecutive purchases using pandas functions for pattern (A B C) (Listing~\ref{lst:UDF-match-recognize}).
\begin{lstlisting}[basicstyle=\ttfamily\footnotesize,language=Python,
                   caption={Apply \texttt{MATCH\_RECOGNIZE} using pandas functions},
                   label={lst:UDF-match-recognize},
                   frame=single]
import pandas as pd
df['order_date'] = pd.to_datetime(df['order_date'])
# Sort for partition
df = df.sort_values(['customer_id', 'order_date']).reset_index(drop=True)
def match_pattern_ABC(group: pd.DataFrame):
    """Find matches where B.price < A.price and C.price < B.price."""
    matches = []
    n = len(group)
    for i in range(n - 2):  # need at least 3 rows for A,B,C
        A = group.iloc[i]
        B = group.iloc[i + 1]
        C = group.iloc[i + 2]

        if (B['price'] < A['price']) and (C['price'] < B['price']):
            matches.append({
                'customer_id': A['customer_id'],
                'start_date': A['order_date'],
                'end_date': C['order_date'],
                'bottom_price': C['price']
            })
    return matches
# Apply per partition
all_matches = []
for cust_id, grp in df.groupby('customer_id'):
    all_matches.extend(match_pattern_ABC(grp))

result_df = pd.DataFrame(all_matches)
print(result_df)
\end{lstlisting}




These systems leave a deployment and workflow gap. Each fits when the data
already lives in its environment or needs distributed or stream processing, but
none is the direct execution path for a Pandas DataFrame already held in a
notebook or script. DuckDB reduces the setup cost because it runs in-process,
yet its row-pattern support relies on translating the query and executing it
inside DuckDB~\cite{lambrecht2025democratize}. What is missing is a
Pandas-native interface that keeps the declarative SQL structure without a
second engine or a transpilation step.

This paper addresses that gap with an in-process engine that executes
\texttt{MATCH\_RECOGNIZE} queries directly on Pandas DataFrames: it takes an SQL
query and a DataFrame and returns the matches as a DataFrame, with no database
server and no data transfer.

For example, an e-commerce platform that tracks all customer purchases, the marketing team wants to
find customers who are decreasing their spending money by buying progressively cheaper items in three
consecutive purchases, by detecting three consecutive purchases using MATCH\_RECOGNIZE for the pattern (A B C) (Listing~\ref{lst:basic-match-recognize}).
\begin{lstlisting}[language=Python,
                   caption={Using \texttt{MATCH\_RECOGNIZE}},
                   label={lst:basic-match-recognize},
                   frame=single]
import pandas as pd
from src.executor.match_recognize import match_recognize
df['order_date'] = pd.to_datetime(df['order_date'])
# Define the MATCH_RECOGNIZE query
query = """
SELECT customer_id, start_date, end_date, bottom_price
FROM orders
MATCH_RECOGNIZE (
  PARTITION BY customer_id
  ORDER BY order_date
  MEASURES
    A.order_date AS start_date,
    C.order_date AS end_date,
    C.price      AS bottom_price
  PATTERN (A B C)
  DEFINE
    B AS B.price < A.price,
    C AS C.price < B.price
);
"""
# Execute and print results
output_df = match_recognize(query, df)
print(output_df)
\end{lstlisting}


After integrating MATCH\_RECOGNIZE into Pandas, the complex operations that were applied before were eliminated. In a single statement, it is possible to define partitioning column(s), ordering key, pattern grammar (e.g., "A B C"), logical definitions for each step, and the summary or detail measures that will be returned. The method returns a clean, annotated DataFrame of full matches. Additionally, it is simple to expand to more intricate patterns, varying lengths, or conditional patterns; simply update the pattern string or definitions to align with specifications. Using the same declarative SQL syntax can be effectively utilized for multiple analytical use cases \cite{petkovic2022rpr}.

The main contributions of this paper are as follows:
\begin{itemize}
  \item \textbf{SQL-based row pattern recognition for Pandas.} An in-process
    engine that executes an R010-style subset of SQL:2016
    \texttt{MATCH\_RECOGNIZE} (row pattern recognition in the \texttt{FROM}
    clause) directly on DataFrames, covering the main clauses, output and skip
    modes, navigation functions, aggregates, and pattern constructs from
    quantifiers and alternation to anchors, exclusions, and \texttt{PERMUTE}.
  \item \textbf{Automata-based execution.} Each pattern is compiled once into
    a finite automaton and executed over ordered DataFrame partitions, with
    explicit guards that reject a pattern whose automaton would exceed a fixed
    budget instead of running it partially.
  \item \textbf{Performance optimization.} A guarded optimization layer of
    vectorized predicates, compiled measures, fused output construction, and
    bounded caching, in which a faster path is used only when it provably
    returns the same answer as the general path.
  \item \textbf{Correctness, performance, and scalability evaluation.} A
    cross-system study against Trino~473 and Oracle~21c EE on real data, in
    which all 30 pattern--size cells agree and the engine records the lowest
    time, together with a scalability test up to 227.9 million rows.
\end{itemize}

\section{Background and Related Work}

This section first examines how ordered data and sequential patterns are
handled in Pandas, the target environment of this work, and then reviews the
systems that implement \texttt{MATCH\_RECOGNIZE} and the approaches proposed to
optimize it.

\subsection{Row Pattern Recognition in Pandas}

Pandas is a popular, open-source Python library for data analysis and
manipulation~\cite{McKinney2010}. Its straightforward installation process and
strong community support make it a good choice for students, researchers, and
professionals who frequently need to analyze data without using complicated
systems like Oracle, Trino, or Snowflake. Pandas is highly popular due to ease
of setup and use, absence of licensing fees, and smooth integration within the
larger Python libraries.

Ordered data is handled by sorting a DataFrame with \texttt{sort\_values} and
splitting it into independent groups with \texttt{groupby}, so that each
customer, sensor, or account is processed in time order. Within each group,
pattern detection is assembled from low-level operations: \texttt{shift} aligns
a row with its neighbours, \texttt{diff} measures the change between consecutive
rows, \texttt{rolling} computes windowed statistics, and Boolean masks combine
these into conditions. For everyday tasks, Pandas offers straightforward methods
for managing data sequences, filtering, grouping, and performing basic
time-series analyses.

However, it has difficulty with advanced pattern detection in contrast to SQL's
\texttt{MATCH\_RECOGNIZE} clause. Pandas lacks a straightforward way to express
complex patterns; users must create their own solutions using functions like
\texttt{rolling}, \texttt{groupby}, or \texttt{shift}. These custom approaches
can become complicated and error-prone, especially as patterns lengthen, need
overlap control, or refer to rows that are already part of a match.

The Pandas API has no native row-pattern primitive, so such logic must be
assembled by hand or sent to another engine. A declarative pattern interface
inside Pandas would keep the data in memory while letting the analyst state what
to find rather than how to find it. Additionally, for datasets that fit
comfortably in memory, tools like Pandas offer a faster and more direct
alternative, eliminating the latency of disk-based operations common to larger
database engines~\cite{Evaluation,in-memory_processing}. This makes Pandas the
target environment of this work.

\subsection{Existing MATCH\_RECOGNIZE Implementations}

Several SQL engines implement \texttt{MATCH\_RECOGNIZE} natively, while others
are still considering it, such as PostgreSQL~\cite{howe2020matchrecognize} and
MariaDB~\cite{mariadb2025regex}. Systems without native support must emulate
row-pattern matching using a combination of window functions, user-defined
aggregates, or external procedural layers—approaches that are often more
complex, less efficient, and harder to maintain~\cite{TURP2,TURP}. This
subsection first summarises the operator and its main clauses, then reviews the
main implementations and optimization approaches, and closes with a comparison.

\paragraph{SQL MATCH\_RECOGNIZE}
The SQL standard distinguishes three optional row-pattern features: R010 (row
pattern recognition in the \texttt{FROM} clause), R020 (row patterns in
\texttt{WINDOW} specifications), and R030 (full aggregate support); this work
targets an R010-style subset~\cite{iso2016,ISO2021}. The general structure of
the clause is shown in Listing~\ref{lst:mr-structure}.
\begin{lstlisting}[language=SQL,frame=single,caption={General structure of the \texttt{MATCH\_RECOGNIZE} clause},label={lst:mr-structure}]
SELECT <columns to return>
FROM <table_name>
MATCH_RECOGNIZE
(
  [ PARTITION BY <columns to group data by> ]
  [ ORDER BY <columns to sort each group> ]
  [ MEASURES <expressions to define output values> ]
  [ ONE ROW PER MATCH | ALL ROWS PER MATCH ]
  [ AFTER MATCH <skip to option> ]
  [ PATTERN ( pattern_expression ) ]
  [ SUBSET <combine multiple variables into one> ]
  DEFINE <rules for each pattern variable>
);
\end{lstlisting}

Row pattern recognition in SQL, as standardized in SQL:2016, detects patterns in sequential data through the 
\texttt{MATCH\_RECOGNIZE} clause. The foundational architecture establishes independent pattern matching scopes via \texttt{PARTITION BY} clauses and defines temporal ordering through \texttt{ORDER BY} specifications within each partition. Pattern definitions utilize regular expression-inspired syntax (e.g., A B+ C?) to express complex event sequences, incorporating fundamental operations such as concatenation, alternation, and quantified repetition through standard quantifiers (\texttt{*}, \texttt{+}, \texttt{?}, \texttt{\{i,j\}}). The \texttt{DEFINE} clause establishes boolean predicates for pattern variables, enabling the incorporation of navigation functions (\texttt{FIRST}, \texttt{LAST}, \texttt{PREV}, \texttt{NEXT}) that facilitate temporal and positional analysis of data relationships with appropriate boundary condition handling. The \texttt{MEASURES} clause enables the extraction of computed values from successful pattern matches, supporting standard functions including \texttt{CLASSIFIER()} for pattern variable identification and \texttt{MATCH\_NUMBER()} for match sequence enumeration, with dual semantic evaluation modes: \texttt{RUNNING} for incremental computation and \texttt{FINAL} for complete match evaluation. \texttt{SUBSET} variables provide pattern abstraction capabilities through hierarchical variable grouping mechanisms.
Pattern anchors (\texttt{\^{}}, \texttt{\$}), exclusion blocks
(\texttt{\{-~\ldots~-\}}), and \texttt{PERMUTE} extend the pattern language
further, and a variable used in \texttt{PATTERN} without a \texttt{DEFINE}
predicate is treated as implicitly true. Match control policies, implemented via \texttt{AFTER MATCH SKIP} directives, govern result cardinality and pattern overlap behavior while determining continuation strategies for subsequent pattern detection iterations, ensuring deterministic matching behavior in compliance with SQL:2016 specifications.

\paragraph{Oracle}
Oracle introduced SQL row-pattern recognition in Database~12c, and Oracle~21c
is a main reference for relational \texttt{MATCH\_RECOGNIZE}
semantics~\cite{oracle2022,book}. It provides a comprehensive and robust
implementation of the clause, well-suited for complex, enterprise-scale
analytics. Its documentation places \texttt{MATCH\_RECOGNIZE} in a table
expression and does not document the window form, and its documented aggregate
support is limited to \texttt{COUNT}, \texttt{SUM}, \texttt{AVG}, \texttt{MAX},
and \texttt{MIN}. However, this power comes with high operational costs,
including licensing fees, and a separate database deployment.

\paragraph{Trino}
Trino is an open-source distributed query engine designed for parallel,
federated query execution across large data sources~\cite{trino2022,trino2021row}.
It supports \texttt{MATCH\_RECOGNIZE} with a syntax close to the SQL:2016
standard, documents row pattern recognition both in the \texttt{FROM} clause and
in window structures, and performs well in distributed data environments. It is
more accessible than Oracle in terms of deployment and cost, but it remains a
query server that requires considerable infrastructure management rather than
an in-process library.

\paragraph{Snowflake}
Snowflake is a cloud-native, managed data platform that provides a
user-friendly \texttt{MATCH\_RECOGNIZE} feature with rich \texttt{DEFINE} and
\texttt{MEASURES} expressions~\cite{snowflake2025match_recognize}. Its engine
uses backtracking, so some pattern and data combinations can take a long time to
execute, and Snowflake therefore recommends selective conditions and bounded
quantifiers. Some row-pattern functions are restricted to particular clauses,
and computational costs relate to the size of the warehouse.

\paragraph{Apache Flink}
Apache Flink is designed for real-time stream processing, allowing rapid
detection of event patterns in continuous data flows. It exposes
\texttt{MATCH\_RECOGNIZE} through Flink SQL, backed by its Complex Event
Processing (CEP) library~\cite{flink}, but its documented implementation is a
streaming subset that lists pattern groups, \texttt{PERMUTE}, anchors,
exclusions, \texttt{ALL ROWS PER MATCH}, and \texttt{SUBSET} among the
unsupported features. While Flink is highly scalable and effective for
high-velocity data, it introduces its own learning curve and assumes a streaming
runtime rather than a batch-oriented DataFrame
workflow~\cite{vsprem2024building,georgiou2025streaming}.

\paragraph{DuckDB}
DuckDB is an in-process analytical database whose Python API can query a Pandas
DataFrame directly from SQL, but it does not yet implement
\texttt{MATCH\_RECOGNIZE}; its roadmap lists the clause as planned
work~\cite{duckdb2026roadmap}. The database group at the University of
T\"ubingen instead translates row-pattern queries into recursive common table
expressions (CTEs) that DuckDB already
executes~\cite{lambrecht2025democratize,findling2025bringing}. This approach
expresses pattern variables, ordering, skip behavior, and measures without
adding a native operator, but it still requires translation and execution
through a second engine.

\paragraph{Existing optimization approaches}
Optimization work on row patterns shares one broad goal: reduce unnecessary work
before or during the automaton scan without changing the query result. Zhu et
al.~\cite{10.14778/3579075.3579090} find pattern variables whose conditions can
be checked independently, use relational joins to remove rows that cannot take
part in a match, and then run the automaton matcher on the smaller input, with
cost estimates guiding the choice. This work addresses a different setting: it
compiles conditions and match plans for in-memory arrays and falls back to the
general execution path when an optimization does not apply.

\paragraph{Comparison}
In terms of documented scope and deployment, Oracle and Snowflake support \texttt{FROM}-clause row patterns and Trino supports both the \texttt{FROM} and window forms; Oracle is proprietary and runs on premises or in the cloud, Snowflake is a proprietary cloud service, and Trino is an Apache~2.0 server or cluster. BigQuery documents the clause and Databricks offers it in beta (Runtime~19.0), both as proprietary cloud services. Apache Flink (Apache~2.0) supports a streaming SQL subset over its complex-event-processing engine on a streaming cluster, while DuckDB (MIT, in-process) has no native clause and relies on an external research transpiler. The proposed engine runs in-process in Python under the MIT license and covers the evaluated R010-style subset. A major limitation shared by all these platforms is the complexity of integrating SQL-based pattern matching with machine learning workflows and other analytics tools~\cite{ML_Workflow,Makrynioti2019sql4mlAD}. Typically, data must be exported from the database to external environments for ML modeling, resulting in data duplication, consistency challenges, and more complicated data pipelines \cite{naphade2025evolution}. Keeping track of multiple versions of the same dataset across systems also increases the risk of errors and inefficiency. For many users especially those with modest analytics needs or who work independently, installing and managing large-scale systems like Oracle, Trino, Snowflake, or Flink can be overly complicated for some users. These users may only need to perform occasional pattern detection and would prefer to avoid the overhead of learning different functions or dealing with varying syntax for similar queries across platforms \cite{8509400}.
Although Oracle, Trino, Snowflake, and Flink each have unique strengths for SQL pattern matching in large-scale or real-time scenarios, they introduce extra costs, infrastructure requirements, and integration issues that can be prohibitive for everyday users. These limitations highlight the value of Pandas, as it offers simpler, memory-based tools and unified workflows, where pattern matching and data analytics can be performed seamlessly and without unnecessary duplication or complexity.


\section{System Design and Methodology}

\subsection{System Architecture}

Our \texttt{MATCH\_RECOGNIZE} implementation follows a modular, five-stage architecture specifically designed for SQL row pattern recognition. The engine executes SQL queries directly on \texttt{pandas} DataFrames~\cite{monierashraf2025rowmatch}, while preserving SQL:2016 semantics for the evaluated R010-style subset~\cite{iso2016,ISO2021,melton2017sqlrpr}. It takes two inputs, an SQL query and a Pandas DataFrame, and returns a result DataFrame. The pipeline consists of five phases: parsing, semantic validation, logical plan construction, pattern compilation, and execution (Fig.~\ref{fig:system-architecture}).

Each stage hands one artifact to the next. Parsing turns the query text into an
abstract syntax tree (AST); semantic validation checks that tree while it is
built; logical-plan construction resolves it into an execution configuration;
pattern compilation turns the pattern into an automaton; and execution applies
that automaton to the DataFrame and assembles the result. The query text is
therefore read only once, and only the last stage touches the input rows. The
stages are design boundaries rather than five separate runtime objects—parsing
and validation share one traversal, and the logical plan is a group of resolved
attributes—but the separation keeps every error close to the clause that caused
it, before any row is matched.

\subsection{SQL Parsing and Logical Plan Construction}

The process starts by analyzing the user's SQL query, identifying its logical components. This proceeds through a parsing process that explores the query, recognizes its main components such as grouping (\texttt{PARTITION BY}), ordering (\texttt{ORDER BY}), the pattern to be searched, and any specific conditions or output metrics, and then organizes these into an Abstract Syntax Tree (AST). The AST provides a clear and structured representation of the query. This approach eases query validation and prepares it for pattern matching in the following stages.

In the parsing stage, the SQL query is transformed into an abstract syntax tree (AST) that captures both the \texttt{SELECT}/\texttt{FROM} clauses and \texttt{MATCH\_RECOGNIZE} subclauses~\cite{tarazona2021antlr,parr2013definitive}. Semantic validation then checks schema references, variable usage, predicates, skip policies, and output modes. Compliance rules are applied to ensure standard conformance, correct use of navigation functions, consistent measure semantics, and robust handling of edge cases such as empty matches, partition boundaries, and skip behaviors.

Validation resolves every name against the pattern. Qualified references in
\texttt{DEFINE} and \texttt{MEASURES} are checked against the pattern variables
and \texttt{SUBSET} aliases, so a condition on \texttt{Q.price} is rejected when
\texttt{Q} does not appear in the pattern, while a variable without a
\texttt{DEFINE} predicate is valid because its predicate is implicitly true.
Function calls must use a supported form, and settings must work together: an
exclusion block combined with \texttt{WITH UNMATCHED ROWS} is rejected because
one removes rows that the other requires, and an \texttt{AFTER MATCH SKIP}
target must name a pattern variable or subset. DataFrame column names are
resolved later, when the configuration is applied to the input.

The validated plan is resolved into a logical plan composed of modular operators for partitioning, sorting, matching, measuring, and skipping. In practice, the logical plan is an execution
configuration of typed fields that represents each clause directly: the
partition keys, the ordering keys with per-key direction and null placement, the
normalized pattern text, the \texttt{DEFINE} mappings, the \texttt{SUBSET}
aliases, the measures with their resolved \texttt{RUNNING} or \texttt{FINAL}
semantics, the rows-per-match mode, and the skip mode with its target. Defaults
are fixed at this point: an omitted null placement becomes \texttt{NULLS LAST},
an explicit \texttt{RUNNING} or \texttt{FINAL} prefix wins, and
\texttt{ONE ROW PER MATCH} uses final values. Later stages read this
configuration instead of reparsing the SQL text.

\subsection{Pattern Matching and Execution Model}

Once the AST is completed, the system focuses on the pattern component described in the SQL query. This pattern is then converted into a finite automaton, which defines a set of states and transitions for detecting complex sequences or behaviors in the data. 
This process begins by constructing a non-deterministic finite automaton (NFA) from the pattern and then, for improved efficiency, transforms it into a deterministic finite automaton (DFA) \cite{georgiou2025streaming}. The DFA  enhances the matching process by removing ambiguity in transitions, enabling the system to scan data sequences quickly and accurately. This compilation process enables the system to handle a wide variety of pattern features, such as repetitions, alternatives, and specific sequences, in a unified and efficient way. The resulting automaton acts as the core mechanism for scanning and detecting patterns within the data.

The execution phase uses the constructed DFA to perform pattern matching directly over input data represented as Pandas DataFrames. The engine begins by partitioning and ordering the data according to the query’s specifications. It then applies the DFA to scan the dataset, identifying all sequences that fit the defined pattern. For every detected match, the engine computes any requested measures or calculations and compiles the results into a DataFrame formatted to mirror standard SQL query outputs. By utilizing Pandas, the system retains both flexibility and accessibility, smoothly incorporating advanced pattern matching into conventional Python data analysis workflows.

Predicate evaluation happens per candidate row. Conditions that depend only on
the current row can be prepared for a whole partition at once, while conditions
that depend on the match built so far are evaluated as that match grows. Each
completed match then passes to measure evaluation and result construction.

Finally, execution is performed over ordered partitions using the compiled automaton. Matches are materialized with the correct \texttt{RUNNING}/\texttt{FINAL} semantics. The evaluation engine manages context separation, applies navigation functions (\texttt{FIRST}, \texttt{LAST}, \texttt{PREV}, \texttt{NEXT}) with partition awareness, and computes aggregates such as \texttt{COUNT}, \texttt{SUM}, and \texttt{AVG} across pattern variables. This preserves SQL:2016 semantics for the supported subset while producing results directly as \texttt{pandas} DataFrames.

\section{Implementation and Optimization}

\subsection{ANTLR4 Grammar and AST Implementation}

Our system reuses the community ANTLR4 grammar for the Trino SQL dialect, whose row-pattern rule already covers all eight \texttt{MATCH\_RECOGNIZE} sub-clauses, so no grammar changes were needed. This grammar was defined by ANTLR4, including complex patterns, nested patterns, alternation, quantifiers, grouping, and exclusions \cite{antlr_trino_sql}. The parser’s output is a detailed parse tree that captures the syntactic structure of each SQL query\cite{parr2013definitive},\cite{tarazona2021antlr}. ANTLR4 generates the lexer, parser, and traversal
scaffolding directly from the rule in Listing~\ref{lst:grammar}.

\begin{lstlisting}[language={},basicstyle=\ttfamily\scriptsize,caption={The \texttt{patternRecognition} rule of the Trino ANTLR4 grammar (whitespace reflowed)},label={lst:grammar}]
patternRecognition
  : aliasedRelation (
      MATCH_RECOGNIZE_ LPAREN_
      ( PARTITION_ BY_ partition += expression
        (COMMA_ partition += expression)* )?
      ( ORDER_ BY_ sortItem (COMMA_ sortItem)* )?
      ( MEASURES_ measureDefinition
        (COMMA_ measureDefinition)* )?
      rowsPerMatch? (AFTER_ MATCH_ skipTo)?
      (INITIAL_ | SEEK_)?
      PATTERN_ LPAREN_ rowPattern RPAREN_
      ( SUBSET_ subsetDefinition
        (COMMA_ subsetDefinition)* )?
      ( DEFINE_ variableDefinition
        (COMMA_ variableDefinition)* )?
      RPAREN_ (AS_? identifier columnAliases?)?
    )?
  ;
\end{lstlisting}

ANTLR4's parse tree is a concrete syntax tree that keeps every keyword and
punctuation token. The engine converts it into a compact typed AST using the
Visitor pattern: two visitors extend the generated base class, one for the outer
query and one for the row-pattern clause, and each sub-clause is stored in a
dataclass with named fields. Expression leaves remain textual by design;
\texttt{DEFINE} predicates and \texttt{MEASURES} expressions are kept as strings
and parsed later by the restricted evaluator.

The core path targets one \texttt{MATCH\_RECOGNIZE} clause inside a top-level
\texttt{SELECT}, with an optional outer \texttt{ORDER BY}. \texttt{DEFINE} is
optional, ordering keys support per-key \texttt{ASC}/\texttt{DESC} direction and
\texttt{NULLS FIRST}/\texttt{NULLS LAST}, and a key may also be an expression
over the input columns. Conditional and subquery ordering keys, rewriting of
\texttt{WITH} clauses, set operations, and general nested subqueries remain
outside the supported path. Syntax errors go through a custom error listener
instead of ANTLR's console default, and each error carries a line, column, and
source snippet; semantic errors are raised by the validation pass before any
automaton is built, so they still name the clause that caused them.

\paragraph{Condition and Measure Evaluation}
A dedicated evaluation subsystem parses SQL pattern conditions and measures into a small expression tree and evaluates it through an allowlist, so user expressions are never executed as Python code; it supports navigation functions and aggregations with SQL:2016 compliant NULL semantics for both running and final calculations.\\ The allowlist covers comparisons, Boolean and arithmetic
operators, literals, \texttt{IN} lists, conditional expressions, qualified
references such as \texttt{A.price}, navigation functions,
\texttt{CLASSIFIER}, \texttt{MATCH\_NUMBER}, and the supported aggregates;
imports, assignments, and access to Python built-ins are never evaluated.

\subsection{Finite Automata-Based Pattern Matching}

\paragraph{Pattern Tokenization}
Pattern expressions are tokenized using a recursive descent tokenization algorithm that supports anchors, grouping, quantifiers, and nested constructs. The tokenizer normalizes the quantifiers \texttt{*},
\texttt{+}, \texttt{?}, and \texttt{\{i,j\}} into minimum and maximum counts
together with a greedy or reluctant preference, where a trailing \texttt{?}
makes a quantifier reluctant, so the builder handles every quantifier through
one internal representation.

\paragraph{NFA Construction}
We use Thompson’s construction algorithm to translate pattern tokens into a Non-deterministic Finite Automaton (NFA). Each state captures transitions, variable bindings, anchors, and metadata for advanced features. Quantifiers (\texttt{*}, \texttt{+}, \texttt{?}, \texttt{\{i,j\}}) are directly mapped to sub-automata, and each transition is guarded by the \texttt{DEFINE} predicate of its variable~\cite{salomaa1996nfa,georgiou2025streaming}. Fig.~\ref{fig:meth-nfa} shows a simplified NFA for
\texttt{A+ B?}: state $q_1$ is reached after one or more \texttt{A} rows and is
accepting because \texttt{B} is optional, an $\varepsilon$-transition leads to
the connector state $r$, and consuming one \texttt{B} row reaches the second
accepting state $q_2$. When several continuations are possible, transition
metadata preserves their pattern order, so greedy quantifiers prefer a longer
valid match, reluctant quantifiers a shorter one, and alternation follows
declaration order. Grouping, alternation, anchors, and exclusions are built the
same way; rows inside an exclusion block still take part in matching, and only
their output is suppressed. \texttt{PERMUTE} over $m$ variables represents all
$m!$ orders.

\paragraph{DFA Construction and Optimization}
The NFA is systematically converted into a Deterministic Finite Automaton (DFA) using subset construction, drastically reducing the number of active states during execution. After construction, unreachable states are removed and transitions are normalized; this reduction is deliberately conservative and does not perform full DFA minimization, which would also merge states that behave identically. The resulting DFA supports efficient row-by-row evaluation while preserving pattern semantics and priorities and custom conditions for accurate pattern semantics \cite{e104-d_3_381,10.1145/986537.986588,georgiou2025streaming}.

\paragraph{Construction limits} Because subset construction is exponential in the worst
case, the compiler is guarded. \texttt{PERMUTE} is rejected above eight
variables or an estimated 50,000 branches, which are one decision, since
$8! = 40{,}320$ stays below that ceiling while $9! = 362{,}880$ exceeds it. DFA
construction is bounded by a ceiling of 50,000 states, which a memory-aware
budget may lower on a constrained system, and by an iteration limit. Reaching
any limit raises an explicit compilation error, so the engine never executes or
caches a partial automaton; none of the evaluated patterns reached these limits.

\subsection{Execution Engine and Performance Optimization}

\paragraph{Execution engine}
The matching engine applies the DFA sequentially over each partition of the DataFrame with specialized handling for anchors, skip modes, and edge cases. The executor coordinates the entire pattern matching process, integrating parsing, automata construction, match identification, and result formatting.

A match never crosses a partition boundary, so the DataFrame is first split on
the \texttt{PARTITION BY} columns, or treated as one partition when there are
none. The engine then checks whether each partition already follows the
complete \texttt{ORDER BY} specification and sorts it otherwise, using a stable
sort so that rows with equal keys keep their DataFrame order. Matching walks the
ordered rows, tests the possible transitions at each position, and applies the
pattern's preference; each completed match records its start, end, variable
assignments, and excluded rows, which drive skip handling and measure
evaluation.

Some predicates depend on the tentative match, for example when accepting a row
changes a running average used by a later condition. These cases use a
preference-ordered depth-first search with backtracking. The search is
iterative, so Python's recursion depth does not limit the match length, and a
state budget and a search budget bound the explored states and steps; exhausting
either raises an explicit error instead of returning a partial or different
match.

After a match, the engine resumes according to the four
\texttt{AFTER MATCH SKIP} modes: past the last row (the default), to the next
row, or to the first or last row of a named variable. Empty matches always
advance by one row, and a target that is absent from the match or points back
to its start raises an error, which prevents a silent loop.
\texttt{ONE ROW PER MATCH} emits one summary row per match, while
\texttt{ALL ROWS PER MATCH} emits every visible matched row and supports
\texttt{SHOW EMPTY MATCHES}, \texttt{OMIT EMPTY MATCHES}, and
\texttt{WITH UNMATCHED ROWS}. Measures are compiled once for common navigation
and aggregate forms; navigation uses bounds-checked lookups that return
\texttt{NULL} out of range, and \texttt{MATCH\_NUMBER()} numbers matches within
each partition. Eligible paths assemble the output columns directly before the
result DataFrame is created.

\paragraph{Performance optimization}
One rule governs the optimization layer: a faster path may never change the
answer. Each technique is switched on only when the engine can prove that it
applies, and the general path takes over otherwise; differential tests compare
every eligible fast path with the general path on the same input and output
mode. Before sorting a partition, the engine checks in $O(n)$ whether the rows
already follow the requested \texttt{ORDER BY} sequence and skips the sort and
its copy when they do. Predicates that depend only on the current row, literals,
and fixed-offset \texttt{PREV}/\texttt{NEXT} are evaluated once per partition as
vectorized column masks, so the matcher reads a Boolean array instead of calling
the expression evaluator for every candidate row. When every variable has a
mask, the DFA runs over compact decision tables, and linear patterns such as
\texttt{A B\{2,4\} C+} use run-length arrays that skip complete runs. For
eligible output modes, matching and result construction are fused, common
measures are compiled into direct array plans, compiled automata are reused
through a bounded least-recently-used (LRU) cache, and partitions are exposed
through a lazy row view with conservative output projection. Separate budgets
bound cache capacity, DFA construction, and exact search; exhausting one raises
an explicit error rather than returning a partial result. A running aggregate in a \texttt{DEFINE} predicate, such as
the running average above, receives an incremental plan that updates the
aggregate as the matched prefix grows and rolls it back on backtracking, which
removes the quadratic cost of recomputing it from the beginning. These choices
lower temporary memory, but they do not make execution streaming: the engine
retains the input and the result, and the budgets bound construction and search
rather than total process memory.

The techniques serve three purposes. Three of them avoid copies: the
ordered-input check, active when the requested \texttt{ORDER BY} sequence is
already present, avoids an unnecessary sort and DataFrame copy; the fused output
drivers, active under the default skip with no unmatched rows, anchors, or empty
matches, an eligible matcher, and fully compiled measures, avoid intermediate
match and row dictionaries; and lazy rows with output projection, active when the
partition path supports lazy access and the selected source columns can be
resolved safely, reduce row copies, retained Python objects, and output width.
The LRU pattern cache serves reuse: when caching is enabled and the complete
automaton fits the cache budget, it eliminates redundant automaton construction
across repeated queries.

The remaining four avoid rework. Vectorized condition masks apply to a row-local
expression, or to safe row-local conjuncts in a mixed \texttt{AND}, and replace
repeated Python evaluation with column operations and exact prefilters.
Row-local DFA decision tables require all predicates to be vectorized, with no
empty-match, anchor, exclusion, \texttt{PERMUTE}, \texttt{SUBSET}, reluctant,
or state-dependent requirement, and replace repeated transition dispatch with
compact indexing and segment assignments. The linear run-length plan needs the
default skip, a plain linear variable sequence, supported quantifiers, and
row-local masks, and it skips complete runs and memoizes failed suffixes.
Compiled measure and prefix plans cover the supported direct navigation and
aggregate forms, reusing prepared array state and avoiding repeated prefix
aggregation.


\section{Experimental Evaluation}

\subsection{Evaluation Methodology}

\subsubsection{Evaluation Criteria and Metrics}

We evaluate the proposed \texttt{MATCH\_RECOGNIZE} engine through the
following criteria and metrics. \texttt{Correctness}: results are compared with
Trino 473 and Oracle 21c EE by row-level equality across multiple pattern
types—the same rows, values, and order where it is deterministic, after
normalizing case-only column-name differences—ensuring identical matching,
pattern alignment, and measure calculations. \texttt{Feature coverage}:
following SQL:2016 \texttt{MATCH\_RECOGNIZE} semantics—including
\texttt{PERMUTE} patterns, exclusions, quantifiers, navigation functions, and
output modes—each main clause is marked supported, partially supported, or
unsupported against the reference tests, and a row-pattern type counts as covered
when at least one test case produces output identical to the reference
systems~\cite{iso2016,ISO2021,monierashraf2025rowmatch}.
\texttt{Developer effort (code size)}: the lines required to express equivalent
logic in idiomatic \texttt{pandas}; baselines typically need substantially more
code (e.g., chained \texttt{groupby}/\texttt{shift}/joins) than a single
\texttt{MATCH\_RECOGNIZE} statement, yielding reduced LOC in line with the row
pattern recognition (RPR) goal of lowering implementation effort
\cite{iso2016,ISO2021,melton2017sqlrpr,Python_UDF}.

\texttt{Execution time}: the client-observed end-to-end latency of one run,
which includes query execution and result materialization or transfer but
excludes data loading. Each pattern--size cell reports the mean of twenty
measured runs after five warm-up runs, with outliers removed by the 1.5$\times$
interquartile range (IQR) rule, which drops a run lying more than 1.5 times the
spread between the 25th and 75th percentiles outside them.
\texttt{Throughput}: computed for each run as the dataset size divided by that
run's time, then filtered and averaged the same way, so it is the mean of the
rates rather than the rate of the mean. \texttt{Query memory}: the incremental
peak, that is, the largest memory sample during the query minus a baseline
averaged over a five-second idle window before it; memory is read every 50\,ms
from the Linux control-group (cgroup v2) counter of the engine process or of the
database container. \texttt{Footprint}: the absolute peak of the same counter,
which includes everything already resident, such as the input DataFrame, the
Java Virtual Machine (JVM) heap of Trino, or the System Global Area (SGA) of
Oracle. \texttt{Scalability}: how execution time and memory grow as the input
grows, measured on real data up to 227,899,533 rows and summarised by a
least-squares linear fit whose $R^2$ is the share of the variation in measured
time that the line explains.

\texttt{MATCH\_RECOGNIZE} implementation using ANTLR4 for parsing Trino SQL, \texttt{pandas} for DataFrame management, and custom AST/NFA/DFA modules for pattern detection.

Every system ran under the same outer limit of one CPU core and 32\,GB of
memory, enforced through Linux control groups: the engine ran in its own control

counter measures all three. For the main benchmark Trino reads from its

\subsection{Complexity Analysis}

Costs are stated in asymptotic notation over five symbols: $n$ input rows, $m$
pattern symbols, $d$ \texttt{DEFINE} variables, $k$ matches, and $\ell$ the
average number of rows per match materialised in the output, so $\ell = 1$
under \texttt{ONE ROW PER MATCH}. Running a query does five kinds of work:
parsing, automaton construction, ordering, condition checking, and matching
with output construction.

Parsing and automaton construction depend on the pattern rather than on the
data. NFA construction is $O(m)$, and the NFA-to-DFA conversion is $O(2^{m})$
states in the worst case but a handful in practice; for a fixed pattern this is
a one-time constant, and the compiled automaton is cached across queries.
Ordering is the only data-dependent cost above linear: a comparison sort costs
$O(n \log n)$ per partition, but the engine first checks in $O(n)$ whether the
rows already follow the requested order and skips the sort when they do.
Condition checking prepares one Boolean result per row and variable on the
compiled row-local path, costing $O(nd)$, and matching with output construction
then costs $O(n + k\ell)$ on the default-skip path.

Two independent axes follow. Along the data axis, with the pattern fixed, the
engine is $\Theta(nd + n + k\ell) = \Theta(n)$ when the input is already
ordered, as it is in the benchmark, and $O(n \log n)$ when a sort is required,
because $d$ is a property of the query rather than of the table and
$k\ell = O(n)$ while matches do not overlap. Along the pattern axis, with the
data fixed, three constructs are expensive in $m$ rather than in $n$: the
NFA-to-DFA conversion, \texttt{PERMUTE}, which expands to $O(m!)$ branches, and
a \texttt{DEFINE} predicate that reads the match built so far, which cannot use
the row-local Boolean matrix and may require the preference-ordered exact
search. Each of the three is either paid once or held in check by the explicit
compiler guards, so none of them appears as a growth curve in the data size.
Extra memory on this compiled path is $O(nd + n + k\ell)$, which reduces to
$O(n)$ for a fixed query with non-overlapping matches. The worst case lies on the
pattern axis: a state-dependent or ambiguous predicate may require the exact
search, whose cost can grow exponentially, which is why that search runs under
an explicit budget.

These bounds are theoretical; the measurements in Section~\ref{sec:empirical}
test them on one machine. The ordered benchmark follows the $\Theta(n)$ case,
and its per-family linear fits give $R^2 = 0.9904$--$0.9997$. The shuffled
scenario measures the $O(n \log n)$ case directly; over the measured 100K--2.22M
range $\log_2 n$ grows only from about 17 to 21, so that case also looks almost
straight and separates from the ordered one by a near-constant factor rather
than a visible bend. A high $R^2$ therefore describes the measured range; it does
not prove the asymptotic bound.

\subsubsection{Sensitivity and Boundary Analysis}
\label{sec:sensitivity}

The main matrix uses input that is already ordered and predicates that depend
only on the current row. Two sensitivity cases remove these advantages. In the
first, every input of the main matrix is deterministically shuffled, so the
engine must take its $O(n \log n)$ sorting branch; all 90 cells still complete
with identical match counts (Table~\ref{tab:ordering_by_size}). The engine slows down by 1.43$\times$ on average,
against 1.04$\times$ for Oracle and 1.11$\times$ for Trino, and at 2,222,742
rows its time rises from 0.43 to 0.63 seconds. The ranking holds: under shuffled
input the engine remains 4.5$\times$ faster than Oracle and 8.8$\times$ faster
than Trino at the full size, against 6.2$\times$ and 11.2$\times$ with ordered
input, so the advantage is not an artifact of the ordered shortcut.

In the second case, the \texttt{simple\_sequence} query's \texttt{DEFINE}
becomes \texttt{B AS category = 'B' AND price > AVG(A.price)}, a running
aggregate that depends on the match so far and therefore cannot use the
row-local Boolean masks. An earlier recorded run that used the generic exact evaluator was the slowest of
the three systems at every size, 64.41 seconds at the full size, because it
recomputed \texttt{AVG(A.price)} each time the tentative match grew. The engine
now evaluates this form with an incremental plan that updates the aggregate as
the match grows. It takes 1.28 seconds at the full size, about 50$\times$ faster
than that run, against 2.32 for Oracle and 8.67 for Trino, leading by 1.2--1.8$\times$
and 5.0--15.9$\times$ across the six sizes with identical output (181,147
matches, Table~\ref{tab:worstcase_coverage}); the database values in this case use two measured runs per size. This
covers one important state-dependent form; other state-dependent or ambiguous
predicates fall back to the exact search, whose worst case is exponential and
which stops with an explicit error when its budget is exhausted.

The advantage comes from specialization rather than from a better general query
engine. The engine runs inside the process that already holds the data, so it
avoids database planning, catalog, transaction, client-protocol, and
data-transfer costs, and its compiler turns supported predicates into column
operations and integer comparisons. The sensitivity cases show that the lead does
not depend on the ordered shortcut: it survives a forced sort and a running
aggregate in \texttt{DEFINE}. Every reported measurement has all optimized paths
enabled, each activating only where it applies, so the results describe the
combined configuration; differential tests show that no fast path changes the
answer, but the study does not isolate the contribution of each technique.

The cost of that speed is per-query memory, where the engine is the highest of
the three at 189.0 MB, while its total footprint stays the lowest in the main
benchmark. That relationship reverses against Oracle at the largest scalability
size, because the engine keeps its DataFrame resident, so speed and memory
residency must be read together.

Measured against the goals stated in the introduction, the results show that an
R010-style subset of \texttt{MATCH\_RECOGNIZE} can run in process on a DataFrame
without a database server, that its results agree with two independent
production engines, and that its execution time grows close to linearly while its
memory grows with the input. These results describe one workstation,
single-partition queries over in-memory input, five pattern families, and default
configurations of all three systems, measured in sequential rather than
concurrent campaigns; other configurations may narrow the measured gaps, and the
results do not establish a general ranking of SQL engines.

\section{Conclusions, Limitations and Future Work}

\paragraph{Conclusions}

We presented a SQL-in-\texttt{pandas} engine for executing \texttt{MATCH\_RECOGNIZE} queries over DataFrames. That provides \texttt{SQL:2016 MATCH\_RECOGNIZE} functionality for 
\texttt{pandas} DataFrames, bridging the gap between the
expressiveness of relational queries and the flexibility of in-memory analytics, bringing SQL pattern matching capabilities to python data science workflows. This opens the door to unified and portable pipelines that preserve both semantics and developer productivity. On the Amazon UK Products benchmark the engine returned the same results as Trino 473 and Oracle 21c EE in all 30 pattern--size cells while averaging 0.17 seconds per cell against 1.04 and 1.98, and it completed the 227.9-million-row Amazon Reviews corpus on every pattern family.

\noindent\texttt{MATCH\_RECOGNIZE} allows data scientists and analysts to use powerful pattern-matching semantics directly within their familiar Pandas environment, without the need for complex Python code or external SQL engine dependencies. This reduces development complexity and enhances productivity for sequential data analysis across domains, including financial analysis, log processing, and time series pattern detection.\\

\paragraph{Limitations}

Despite the system’s comprehensive capabilities, several limitations remain. First,

\noindent\texttt{complex pattern and quantifier interactions}: although the system supports concatenation, alternation, grouping, and standard quantifiers (\texttt{*}, \texttt{+}, \texttt{?}, \texttt{\{i,j\}}), certain combinations—particularly multiple greedy quantifiers nested within groups (e.g.,\texttt{(A+B*)
+C?})can trigger exponential state-space growth during automata construction. This issue primarily arises with three or more levels of nesting combined with unbounded quantifiers; by contrast, simpler patterns and bounded quantifiers behave efficiently. Second, \texttt{limited support for aggregate functions}: while a wide range of built-in aggregates (including conditional and statistical functions) is supported, the current implementation offers only limited support for user-defined aggregate functions. Third, \texttt{SQL:2016 coverage}: the engine implements an evaluated R010-style subset rather than the full standard; the window form (R020), conditional and subquery ordering keys, and vendor-specific extensions are outside it. Fourth, \texttt{memory}: the input DataFrame and the result must stay resident, so available RAM bounds the largest input and the engine is not an out-of-core system. Fifth, \texttt{generalization}: the measurements come from one workstation, single-partition queries, five pattern families, and default configurations of all three systems, so other hardware, many small partitions, wider schemas, or tuned databases may change the measured gaps.

\paragraph{Future Work}

By addressing the identified limitations and implementing the future enhancements, our goal is to develop a more adaptable and efficient solution. That can handle complex pattern-matching scenarios across various data processing environments. Future work will focus on addressing current limitations through enhanced SQL clause support, distributed processing capabilities, and advanced analytics integration. This development roadmap outlined above provides a clear path for improving performance for the current implementation.\\

We plan to extend the engine through some updates,
\texttt{Memory Residency on Large Datasets:} the engine completed the full 227.9-million-row corpus, but it keeps the input DataFrame resident in memory, so available RAM bounds the largest input, and an out-of-core or columnar backend would lift that limit; \texttt{Memory Usage for Large Patterns:} patterns with many variables and complex quantifiers can generate large automata that increase memory consumption; \texttt{ Integration with Query Optimizers:}because the pattern-matching engine currently operates independently of database query optimizers, it may miss plan-level optimization opportunities; \texttt{Pattern Compilation:} full DFA minimization, stronger state pruning, and a faster exact search for state-dependent predicates would reduce construction cost and widen the compiled fast paths; \texttt{Parallel Processing:} independent partitions are a natural unit of parallel work and could run in separate workers while preserving deterministic output order; \texttt{Execution Engine:} a backend abstraction targeting Polars or Apache Arrow, together with a per-technique ablation of the optimization layer, would extend the engine and quantify what each fast path contributes.

\subsection{Measurement Provenance and Reproducibility}

All systems ran sequentially, one at a time, so they never competed for the

\paragraph{Benchmark protocols}
The evaluation used four fixed protocols:
\begin{itemize}
  \item \textbf{Cross-system matrix.} One CPU core, an outer 32\,GB memory
    limit, five warm-up runs, and twenty measured runs on ordered input. The
    matrix contains five patterns and six sizes (100K--2,222,742 rows), giving
    30 cells per system; all 90 cells completed.
  \item \textbf{Stress test.} One CPU core, a 58\,GB memory limit, two warm-up
    runs, five measured runs, and a 600\,s limit per query, over five patterns
    and seven sizes (5M--227,899,533 rows). The proposed engine and Oracle
    completed 35 of 35 cells; Trino completed 33 of 35, because
    \texttt{complex\_nested} reached the time limit at 160M and 227,899,533 rows.
  \item \textbf{Ordering test.} The matrix protocol was repeated after a
    deterministic shuffle, which removes physical pre-ordering while keeping
    the same logical \texttt{ORDER BY} key. All 90 shuffled cells completed.
  \item \textbf{State-dependent test.} One CPU core and a 32\,GB memory limit,
    with ordered input and \texttt{B AS category='B' AND price > AVG(A.price)}.
    The proposed engine used five warm-up runs and twenty measured runs per
    size; the retained Trino and Oracle values contain two measured runs per
    size, so their means are useful for comparison but provide less evidence
    about variation. All 18 cells completed.
\end{itemize}

Memory was sampled every 50\,ms from \texttt{memory.current}, the total that
version~2 of the Linux control-group (cgroup) interface reports for a group of
processes. The incremental peak subtracts a five-second pre-query baseline.
For the proposed engine the absolute peak covers its process; for Trino and
Oracle it covers the full database container. Timing includes query execution
and result construction or retrieval, while data generation and loading are
excluded. MB and GB in the memory tables mean MiB and GiB.

No complete benchmark cell was omitted. The 1.5$\times$ IQR rule could remove
individual samples from a cell, and the number removed was retained with the
measurements. A complete cell may be rejected only when there is recorded

\subsection{Full SQL Syntax Reference} \label{Full_SQL}
\begin{verbatim}
SELECT <select list>
FROM <source table>
MATCH_RECOGNIZE
(
  [ PARTITION BY <partition list> ]
  [ ORDER BY <order by list> ]
  [ MEASURES <measure list> ]
  [ ONE ROW PER MATCH | ALL ROWS PER MATCH ]
  [ AFTER MATCH <skip-to-option> ]
  PATTERN ( <row pattern> )
  [ SUBSET <subset list> ]
  DEFINE <definition list>
) AS <table alias>;
\end{verbatim}

\subsection{Step-by-Step Execution Analysis}\label{Step-by-Step}
\begin{enumerate}
  \item \textbf{Query Parsing: In this step SQL parser extracts components from the query.}\\ Input: Raw SQL query string\\ Process: ANTLR4 parsing of each clause into an abstract syntax tree (AST)\\ Output: AST with the parsed components.\\
    The parser extracts:
    \begin{itemize}
      \item \texttt{PARTITION BY: customer\_id} \\
      To group the data by customer\_id, meaning pattern matching will be performed separately for each customer
      \item \texttt{ORDER BY: order\_date}\\
     To sort data within each partition chronologically by order\_date to establish sequence order 
      \item \texttt{MEASURES:}
        \begin{itemize}
          \item \texttt{start\_date = A.order\_date}
          \item \texttt{end\_date   = C.order\_date}
          \item \texttt{bottom\_price = C.price}
        \end{itemize}
    To define what values to extract from matched patterns. Each measure specifies which variable's column value to return in the result.
        
      \item \texttt{PATTERN: (A B C)}\\
     To specify the sequence pattern to match exactly 3 consecutive rows labeled A, B, and C
      
      \item \texttt{DEFINE:}
        \begin{itemize}
          \item \texttt{B AS B.price < A.price}
          \item \texttt{C AS C.price < B.price}
        \end{itemize}
    \end{itemize}
    To define conditions for each pattern variable must be satisfied. \\ {B} must have lower price than {A} and {C} must have a lower price than {B}.\\
  \item \textbf{Data Partitioning}\\
    To groupby operation splits the DataFrame into separate groups based on the PARTITION BY columns.\\
    Input: partition\_by columns: df.groupby(['customer\_id']) \\Output: Two separate DataFrames, one per customer.\\
    
    \begin{tabular}{llr}
    \multicolumn{3}{l}{\emph{Group 1 -- cust\_1}}\\
    customer\_id & order\_date & price\\\hline
    cust\_1      & 2020-05-11  & 100\\
    cust\_1      & 2020-05-12  & 200\\
    cust\_1      & 2020-05-14  & 100\\
    cust\_1      & 2020-05-16  &  50\\
    cust\_1      & 2020-05-17  & 100
    \end{tabular}
    \quad
    \begin{tabular}{llr}
    \multicolumn{3}{l}{\emph{Group 2 -- cust\_2}}\\
    customer\_id & order\_date & price\\\hline
    cust\_2      & 2020-05-13  &   8\\
    cust\_2      & 2020-05-15  &   4\\
    cust\_2      & 2020-05-18  &   6
    \end{tabular}

  \item \textbf{Pattern Matching for \texttt{cust\_1}}  \\
  Tries to match the pattern starting from each possible row position. Here, row~$k$ is the position in the original table and Row/Index~$k$ the position within the partition; the three rows A, B, and C must be consecutive.\\
    \begin{itemize}
      \item \emph{Attempt 1 (row~0, price=100):} \\
      Try to build pattern A-B-C starting from the first row
        \begin{itemize}
          \item A = row 0 (100):Row 0 (date=2020-05-11, price=100)
          \item B: the next row must satisfy $B.price < A.price$ (price $< 100$)\\
          Index 1: price=200 → $200 < 100$? FALSE \\
          No valid B found, PATTERN MATCH FAILED\\\\
        \end{itemize}
      \item \emph{Attempt 2 (row~1, price=200):}
        \begin{itemize}
          \item A = row1 (200): Row 1 (date=2020-05-12, price=200)  
          \item B = row3 (100) :Row 2 (date=2020-05-14, price=100)  \\Index 2: price=100 → $100 < 200$?   TRUE 
          \item C  =row5 (50): Row 3 (date=2020-05-16, price=50)
          \\Index 3: price=50 → $50 < 100$? TRUE
          \\row5 (50) \(\Rightarrow\) \emph{match found (rows 1, 3, 5)}
        \\Match Dictionary:  {\{'A': 1, 'B': 2, 'C': 3\}}\\
        \end{itemize}
      \item \emph{Attempt 3 (row~6, price=100):}\\
      The default \texttt{AFTER MATCH SKIP PAST LAST ROW} resumes after the last matched row (Row 3)
        \begin{itemize}
          \item A = row6 (100): Row 4 (date=2020-05-17, price=100)
          \item B: no row after Row 4 \(\Rightarrow\) \emph{no match}
          \\PATTERN MATCH FAILED
        \end{itemize}
    \end{itemize}

  \item \textbf{Pattern Matching for \texttt{cust\_2}}  
    \begin{itemize}
       \item \emph{Attempt 1 (row~2, price=8):}
        \begin{itemize}
          \item A = row2 (8): Row 0 (date=2020-05-13, price=8)
         \item  B = row4 (4): Row 1 (date=2020-05-15, price=4) \\ (Look for row where $B.price < A.price$ ($price < 8$)
          \\Index 1: price=4 → $4 < 8$? TRUE 
          \item C: Look for row where $C.price < B.price$ ($price < 4$)
        \\ Index 2: price=6 → $6 < 4$? FALSE
        \\  No valid C found, PATTERN MATCH FAILED\\
        \end{itemize}
        
      \item \emph{Attempt 2 (row~4, price=4):}
        no B \(\Rightarrow\) no match
        \begin{itemize}
          \item A = row4 (4): Row 1 (date=2020-05-15, price=4)
         \item  B: Look for row where $B.price < A.price$ ($price < 4$)
          \\Index 2: price=6 → $6 < 4$? FALSE
          \\No valid B found, PATTERN MATCH FAILED
          \item C: cannot form a complete 3-row pattern
        \\  PATTERN MATCH FAILED
        \end{itemize}
        
    \end{itemize}

  \item \textbf{Apply Measures}\\
  The evaluate\_measure function extracts specific column values from the matched pattern rows according to the MEASURES clause.\\
    Only one match: \texttt{cust\_1} at rows 1, 3, 5.
    \\input:Match dictionary: {'A': 1, 'B': 2, 'C': 3} (from cust\_1)

Measures: \texttt{\{'start\_date': 'A.order\_date',
'end\_date': 'C.order\_date',\\
'bottom\_price': 'C.price'\}}

\begin{description}
  \item[start\_date = A.order\_date] 
    Extract \texttt{order\_date} from the row matched to variable A.  
    \\A is at index 1: \texttt{df.iloc[1][\char`\'order\_date\char`\'}] = \texttt{\char`\'2020-05-12\char`\'}.
  \item[end\_date = C.order\_date] 
    Extract \texttt{order\_date} from the row matched to variable C.\\  
    C is at index 3: \texttt{df.iloc[3][\char`\'order\_date\char`\'}] = \texttt{\char`\'2020-05-16\char`\'}.
  \item[bottom\_price = C.price] 
    Extract \texttt{price} from the row matched to variable C.\\  
    C is at index 3: \texttt{df.iloc[3][\char`\'price\char`\'}] = 50.
  \item[customer\_id] 
    The partition key identifies which group this match belongs to  
    Value: \texttt{\char`\'cust\_1\char`\'}.
\end{description}

 \item \textbf{ Outputs:\\}


Our goal is to represent a detected pattern in customer behavior.

\paragraph{Pattern Meaning}
\begin{itemize}
  \item \textbf{Customer:} \texttt{cust\_1}
  \item \textbf{Pattern Type:} Consecutive price decline ($A > B > C$)
  \item \textbf{Time Period:} 2020-05-12 to 2020-05-16 (4 days)
  \item \textbf{Price Sequence:} 200 \(\to\) 100 \(\to\) 50
  \item \textbf{Business Insight:} Customer \texttt{cust\_1} exhibited a consistent downward trend in order values.\\
\end{itemize}

 The final step assembles all successful matches into a result \texttt{DataFrame}.
\begin{description}

  \item[Input:] List of result rows (one per successful match)
  \item[Process:] \texttt{pd.DataFrame(results)}
  \item[Output:] Final result \texttt{DataFrame}
\end{description}

\end{enumerate}
