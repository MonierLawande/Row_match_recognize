\begin{abstract}
SQL:2016 introduced \texttt{MATCH\_RECOGNIZE} to find user-defined patterns
in ordered table rows. In Pandas, the same task usually needs loops or a
combination of grouping, shifts, and Boolean masks. We present an engine that
takes an SQL query and a Pandas DataFrame and returns a result DataFrame in
the same Python process. It supports a tested subset of row pattern
recognition in the \texttt{FROM} clause, including partitioning, ordering,
pattern definitions, measures, and match-control modes. The engine parses the
query, compiles the pattern into finite automata, and uses vectorized
operations when the query allows them. Other supported cases use general
evaluation or exact search with explicit limits. We compare the engine with
Trino~473 and Oracle~21c EE on five pattern families and six sizes of the
Amazon UK Products dataset, up to 2,222,742 rows. All 30 pattern--size combinations return
identical normalized results across the three systems. Mean execution time
per combination is 0.17 seconds for the proposed engine, 1.04 for Oracle, and
1.98 for Trino. A separate Amazon Reviews 2023 study reaches 227,899,533 rows,
and the engine completes all 35 combinations. These results support SQL row
pattern analysis within Pandas under the tested single-core, single-partition
conditions. Exact search can still be costly, and the input and output must
fit in memory.
\end{abstract}

\section{Introduction}
Row pattern recognition searches an ordered sequence of table rows or stream
events for relationships that span several rows. It can identify trends,
repeated events, and shapes such as a fall followed by a recovery. Applications
include transaction chains related to money
laundering~\cite{10.5120/ijca2022922446} and suspicious user behavior in security
logs~\cite{zemke2007pattern}. Patterns use syntax similar to regular expressions,
but they match rows rather than individual characters.

The \texttt{MATCH\_RECOGNIZE} (MR) clause was introduced in
SQL:2016~\cite{iso2016,ISO2021}. It lets users describe a row pattern, the
conditions that define its variables, and the values to return from each match.
Implementations discussed in this paper include Oracle~21c~\cite{oracle2022,book},
Trino~473~\cite{trino2022,trino2021row},
Snowflake~\cite{snowflake2025match_recognize}, and Apache
Flink~\cite{flink}. These systems support different processing environments and
sets of features, as reviewed in Section~2.

Pandas is widely used for data analysis in Python~\cite{McKinney2010}.
The Pandas API used in this work does not provide a native
\texttt{MATCH\_RECOGNIZE} operator~\cite{pandas233api}.
Users can combine operations such as \texttt{groupby}, \texttt{shift}, and
Boolean masks to detect simple patterns. More complex patterns require code
that handles row positions, repetitions, earlier matched rows, and where the
next search starts. For example, finding three consecutive purchases with
decreasing prices in each customer's history requires both price comparisons
and control of overlapping matches. Extending this code to longer or optional
sequences can be difficult.

The available SQL implementations are useful when data is already stored in a
database or when distributed or stream processing is needed. A Pandas user,
however, may already have the data in a notebook or script. DuckDB reduces
setup because it runs in the same process, but the cited row-pattern approach
translates the query and executes it inside
DuckDB~\cite{lambrecht2025democratize}. The gap addressed here is direct,
declarative row pattern recognition within Pandas DataFrame processing,
without requiring the user to write a procedural matching loop or move the
data to a separate query service.

This paper presents an in-process engine that accepts an SQL
\texttt{MATCH\_RECOGNIZE} query and a Pandas DataFrame and returns a result
DataFrame. The SQL statement brings the pattern, conditions, ordering, and
output measures together, while the result remains available for further
Pandas analysis. The procedural and SQL versions of the consecutive-price
example are given in Appendix~\ref{Step-by-Step}.

The main contributions of this paper are as follows:
\begin{itemize}
  \item \textbf{SQL-based row pattern recognition for Pandas.} An in-process
    engine executes an R010-style subset of SQL:2016
    \texttt{MATCH\_RECOGNIZE}, which specifies row patterns in the
    \texttt{FROM} clause, directly on DataFrames. It supports the main
    clauses, pattern constructs, navigation functions, aggregates, and output
    and skip modes described in this paper.
  \item \textbf{Automata-based execution.} Patterns are compiled into finite
    automata and evaluated over ordered DataFrame partitions. The execution
    model also handles conditions that depend on earlier rows in a match.
  \item \textbf{Performance optimization.} The engine combines vectorized
    predicate evaluation, compiled measures, efficient result construction,
    and bounded caching. Each optimization is used only for supported cases,
    and differential tests compare optimized and general evaluation.
  \item \textbf{Correctness, performance, and scalability evaluation.} A
    cross-system study compares the engine with Trino~473 and Oracle~21c EE.
    All systems return the same results in the 30 pattern--size cells of the
    main benchmark, and the proposed engine has the lowest execution time in
    each cell. A separate scalability test covers up to 227.9 million rows.
\end{itemize}

\section{Background and Related Work}

This section describes how Pandas handles ordered data and row patterns. It
then reviews existing \texttt{MATCH\_RECOGNIZE} implementations and approaches
to optimizing them.

\subsection{Row Pattern Recognition in Pandas}

Pandas is an open-source Python library for data analysis and
manipulation~\cite{McKinney2010}. Its DataFrame interface supports tabular
processing and works with other Python libraries. It is the target environment
of this work.

Ordered data is handled by sorting a DataFrame with \texttt{sort\_values} and
splitting it into independent groups with \texttt{groupby}, so that each
customer, sensor, or account is processed in time order. Within each group,
pattern detection uses several operations: \texttt{shift} aligns
a row with its neighbors, \texttt{diff} measures the change between consecutive
rows, \texttt{rolling} computes windowed statistics, and Boolean masks combine
these into conditions. These methods support filtering, grouping, and basic
time-series analysis, but Pandas has no native row-pattern operator. Users must
write the matching logic themselves or send the data to another engine. Custom
code becomes harder to manage when patterns grow, require overlap control, or
refer to rows already assigned to the current match.

A declarative pattern interface inside Pandas would let the analyst describe
the pattern while keeping the data in memory. In-process execution also avoids a
separate database deployment and client transfer for data already held in a
DataFrame. Its performance relative to a database still depends on the workload
and storage configuration.

\subsection{Existing MATCH\_RECOGNIZE Implementations}

Several SQL engines implement \texttt{MATCH\_RECOGNIZE} natively. Systems
without native support can express row-pattern matching through window
functions, user-defined aggregates, or procedural
code~\cite{findling2025bringing,lambrecht2025democratize}. These alternatives
can require more code and can be harder to maintain. Their performance depends
on the query and execution plan. This subsection summarizes the operator and its
main clauses, reviews the implementations and optimization approaches, and
compares their scope.

\paragraph{SQL MATCH\_RECOGNIZE}
The SQL standard distinguishes three optional row-pattern features: R010 (row
pattern recognition in the \texttt{FROM} clause), R020 (row patterns in
\texttt{WINDOW} specifications), and R030 (full aggregate support); this work
targets an R010-style subset~\cite{iso2016,ISO2021}. The general structure of
the clause is shown in Listing~\ref{lst:mr-structure}.
\begin{lstlisting}[language=SQL,frame=single,caption={General structure of the \texttt{MATCH\_RECOGNIZE} clause},label={lst:mr-structure}]
SELECT <columns to return>
FROM <table_name>
MATCH_RECOGNIZE
(
  [ PARTITION BY <columns to group data by> ]
  [ ORDER BY <columns to sort each group> ]
  [ MEASURES <expressions to define output values> ]
  [ ONE ROW PER MATCH | ALL ROWS PER MATCH ]
  [ AFTER MATCH <skip to option> ]
  PATTERN ( pattern_expression )
  [ SUBSET <combine multiple variables into one> ]
  [ DEFINE <rules for pattern variables> ]
);
\end{lstlisting}

The \texttt{PARTITION BY} clause divides the rows into independent groups, and
\texttt{ORDER BY} sets their order within each group. Patterns use syntax
similar to regular expressions, such as \texttt{A B+ C?}. The main operations
are concatenation, alternation, and repetition, with quantifiers such as
\texttt{*}, \texttt{+}, \texttt{?}, and \texttt{\{i,j\}}.

The \texttt{DEFINE} clause gives each pattern variable a Boolean condition.
Navigation functions such as \texttt{FIRST}, \texttt{LAST}, \texttt{PREV}, and
\texttt{NEXT} allow conditions to refer to other rows, with defined behavior at
the boundaries. The \texttt{MEASURES} clause specifies the output values for
each match. It can use \texttt{CLASSIFIER()} to identify the variable assigned
to a row and \texttt{MATCH\_NUMBER()} to number the matches. Measures can use
\texttt{RUNNING} values, computed up to the current row, or \texttt{FINAL}
values, computed over the complete match. A \texttt{SUBSET} alias combines
primary pattern variables into a union variable.

Other pattern constructs include anchors (\texttt{\^{}}, \texttt{\$}),
exclusion blocks (\texttt{\{-~\ldots~-\}}), and \texttt{PERMUTE}. A variable
used in \texttt{PATTERN} without a \texttt{DEFINE} condition has an implicit
true condition. The \texttt{AFTER MATCH SKIP} clause sets where the next search
starts and therefore controls whether matches can overlap. Pattern preferences
determine which match is selected when several matches are possible in the
supported subset.

\paragraph{Oracle}
Oracle introduced SQL row-pattern recognition in Database~12c, and Oracle~21c
is a main reference for relational \texttt{MATCH\_RECOGNIZE}
semantics~\cite{oracle2022,book}. Its documentation places
\texttt{MATCH\_RECOGNIZE} in a table expression and does not document the
window form. Its documented aggregate support is limited to
\texttt{COUNT}, \texttt{SUM}, \texttt{AVG}, \texttt{MAX},
and \texttt{MIN}. Oracle uses a proprietary license and requires a separate
database deployment.

\paragraph{Trino}
Trino is an open-source distributed query engine designed for parallel,
federated query execution across large data sources~\cite{trino2022,trino2021row}.
It supports \texttt{MATCH\_RECOGNIZE} with a syntax close to the SQL:2016
standard. It documents row pattern recognition both in the \texttt{FROM} clause
and in window structures~\cite{TrinoDocumentation}. It uses a query server or cluster that must be deployed
and managed separately from the Python process.

\paragraph{Snowflake}
Snowflake is a managed cloud data platform that supports
\texttt{MATCH\_RECOGNIZE}, including \texttt{DEFINE} conditions and
\texttt{MEASURES} expressions~\cite{snowflake2025match_recognize}. Its engine
uses backtracking, so some pattern and data combinations can take a long time to
execute, and Snowflake therefore recommends selective conditions and bounded
quantifiers. Some row-pattern functions are restricted to particular clauses,
and execution costs depend on the warehouse size.

\paragraph{Apache Flink}
Apache Flink is designed for stream processing and event-pattern detection in
continuous data. It provides \texttt{MATCH\_RECOGNIZE} through Flink SQL,
backed by its Complex Event Processing (CEP) library~\cite{flink}. Its
version~1.20 documentation describes a streaming subset that lists pattern
groups, \texttt{PERMUTE}, anchors,
exclusions, \texttt{ALL ROWS PER MATCH}, and \texttt{SUBSET} among the
unsupported features. It requires a separate processing runtime, which differs
from working directly with a DataFrame in a Python script.

\paragraph{DuckDB}
Research on DuckDB, an in-process analytical database, translates row-pattern
queries into recursive common table expressions (CTEs) that the database can
execute~\cite{lambrecht2025democratize,findling2025bringing}. This approach
expresses pattern variables, ordering, skip behavior, and measures without
adding a native operator, but it still requires translation and execution
through a second engine.
The DuckDB roadmap still lists native \texttt{MATCH\_RECOGNIZE} as planned
work in October~2026~\cite{duckdb2026roadmap}.

\paragraph{Existing optimization approaches}
Work on row-pattern optimization aims to reduce unnecessary work before or
during the automaton scan without changing the query result. Zhu et
al.~\cite{10.14778/3579075.3579090} find pattern variables whose conditions can
be checked independently, use relational joins to remove rows that cannot take
part in a match, and then run the automaton matcher on the smaller input, with
cost estimates guiding the choice. Our engine compiles conditions and match
plans for in-memory arrays. It uses the general execution path when an
optimization does not apply.

\section{System Design and Methodology}

\subsection{System Architecture}

Our \texttt{MATCH\_RECOGNIZE} implementation has five stages. The engine runs SQL queries directly on Pandas DataFrames~\cite{monierashraf2025rowmatch} and follows SQL:2016 semantics for the evaluated R010-style subset~\cite{iso2016,ISO2021,michels2018new}. It takes an SQL query and a Pandas DataFrame as input and returns a result DataFrame. The five stages are parsing, semantic validation, logical plan construction, pattern compilation, and execution (Fig.~\ref{fig:system-architecture}).

Each stage passes its output to the next. Parsing converts the query text into
an abstract syntax tree (AST). Semantic validation checks the tree while it is
built, and logical plan construction turns it into an execution configuration.
Pattern compilation builds an automaton. The execution stage then selects a
matching plan, applies it to the DataFrame, and builds the result. The query
text is parsed once, and only the execution stage reads the input rows. These
stages describe the design; they are not five separate runtime objects.
Parsing and validation share one traversal, and the logical plan is a group of
resolved attributes. Query errors can therefore be reported with the relevant
clause before matching starts.

\subsection{SQL Parsing and Logical Plan Construction}

The parser identifies the query clauses and stores them in an AST. This
includes the outer \texttt{SELECT}/\texttt{FROM} clauses and the
\texttt{MATCH\_RECOGNIZE} subclauses, such as partitioning
(\texttt{PARTITION BY}), ordering (\texttt{ORDER BY}), the pattern,
conditions, and measures~\cite{antlr_trino_sql,parr2013definitive}.
Semantic validation checks pattern-variable references, supported expressions,
skip policies, and output modes. Input column names are resolved against the
DataFrame at execution time. These checks enforce the supported combinations
before matching begins.

Validation checks references to pattern variables. Qualified references in
\texttt{DEFINE} and \texttt{MEASURES} are checked against the pattern variables
and \texttt{SUBSET} aliases, so a condition on \texttt{Q.price} is rejected when
\texttt{Q} does not appear in the pattern, while a variable without a
\texttt{DEFINE} predicate is valid because its predicate is implicitly true.
Function calls must use a supported form, and clause settings must be
compatible. For example, an exclusion block cannot be combined with
\texttt{WITH UNMATCHED ROWS}, and an \texttt{AFTER MATCH SKIP} target must
name a pattern variable or subset.

The validated AST is resolved into a logical plan for partitioning, sorting,
matching, measuring, and skipping. This plan is an execution
configuration of typed fields that stores each clause directly: the
partition keys, the ordering keys with per-key direction and null placement, the
normalized pattern text, the \texttt{DEFINE} mappings, the \texttt{SUBSET}
aliases, the measures with their resolved \texttt{RUNNING} or \texttt{FINAL}
semantics, the rows-per-match mode, and the skip mode with its target. Defaults
are set at this point: an omitted null placement becomes \texttt{NULLS LAST},
an explicit \texttt{RUNNING} or \texttt{FINAL} prefix takes priority, and
\texttt{ONE ROW PER MATCH} uses final values. Later stages read this
configuration instead of reparsing the SQL text.

\subsection{Pattern Matching and Execution Model}

The execution model combines the resolved query configuration, the compiled
pattern, and the input DataFrame. Pattern compilation prepares a representation
of the allowed row sequences and their matching preferences. The same compiled
pattern can then be used across the query's partitions.

The executor first divides the DataFrame by the \texttt{PARTITION BY} keys and
orders each partition by the \texttt{ORDER BY} keys. Matching searches these
ordered rows for sequences allowed by the pattern. The \texttt{DEFINE}
predicates determine whether a candidate row can be assigned to a pattern
variable, using the current row and, where required, the earlier assignments in
the match. The skip policy determines where the next search begins after a
match is found.

Completed matches pass to measure evaluation. Navigation functions and
supported aggregates use the partition and match context, with the requested
\texttt{RUNNING} or \texttt{FINAL} semantics. The rows-per-match mode determines
which rows are returned. Result construction then combines the selected rows,
partition keys, and measures into an output DataFrame. Section~4 explains the
matching algorithms, execution paths, and optimizations used in these stages.

\section{Implementation and Optimization}

\subsection{ANTLR4 Grammar and AST Implementation}

The system uses the community ANTLR4 grammar for the Trino SQL dialect. Its
row-pattern rule covers all eight \texttt{MATCH\_RECOGNIZE} subclauses, so
no grammar changes were needed. The grammar supports nested patterns,
alternation, quantifiers, grouping, and exclusions~\cite{antlr_trino_sql}.
The parser produces a parse tree that represents the query
syntax~\cite{parr2013definitive,antlr_trino_sql}. ANTLR4 generates the lexer,
parser, and traversal classes from the rule in Listing~\ref{lst:grammar}.

\begin{lstlisting}[language={},basicstyle=\ttfamily\scriptsize,caption={The \texttt{patternRecognition} rule of the Trino ANTLR4 grammar (whitespace reflowed)},label={lst:grammar}]
patternRecognition
  : aliasedRelation (
      MATCH_RECOGNIZE_ LPAREN_
      ( PARTITION_ BY_ partition += expression
        (COMMA_ partition += expression)* )?
      ( ORDER_ BY_ sortItem (COMMA_ sortItem)* )?
      ( MEASURES_ measureDefinition
        (COMMA_ measureDefinition)* )?
      rowsPerMatch? (AFTER_ MATCH_ skipTo)?
      (INITIAL_ | SEEK_)?
      PATTERN_ LPAREN_ rowPattern RPAREN_
      ( SUBSET_ subsetDefinition
        (COMMA_ subsetDefinition)* )?
      ( DEFINE_ variableDefinition
        (COMMA_ variableDefinition)* )?
      RPAREN_ (AS_? identifier columnAliases?)?
    )?
  ;
\end{lstlisting}

ANTLR4's parse tree keeps every keyword and punctuation token. The engine
converts it into a compact typed AST using the
Visitor pattern. Two visitors extend the generated base class: one handles
the outer query and the other handles the row-pattern clause. Each subclause
is stored in a dataclass with named fields. Expression leaves are kept as
text. The restricted evaluator later parses the \texttt{DEFINE} predicates
and \texttt{MEASURES} expressions.

The main execution path supports one \texttt{MATCH\_RECOGNIZE} clause inside a top-level
\texttt{SELECT}, with an optional outer \texttt{ORDER BY}. \texttt{DEFINE} is
optional, ordering keys support per-key \texttt{ASC}/\texttt{DESC} direction and
\texttt{NULLS FIRST}/\texttt{NULLS LAST}, and a key may also be an expression
over the input columns. Conditional and subquery ordering keys, rewriting of
\texttt{WITH} clauses, set operations, and general nested subqueries remain
outside the supported path. A custom error listener replaces ANTLR's default
console messages. Each syntax error includes a line number, column number,
and source snippet. The validation pass reports semantic errors with the
relevant clause before automaton construction starts.

\paragraph{Condition and Measure Evaluation}
The expression evaluator parses SQL pattern conditions and measures into a
small expression tree. It evaluates only allowed operations, so user
expressions are never executed as Python code. It supports navigation
functions and aggregates with SQL NULL semantics for the supported running
and final forms. The allowed operations include comparisons, Boolean and arithmetic
operators, literals, \texttt{IN} lists, conditional expressions, qualified
references such as \texttt{A.price}, navigation functions,
\texttt{CLASSIFIER}, \texttt{MATCH\_NUMBER}, and the supported aggregates;
imports, assignments, and access to Python built-ins are never evaluated.

\subsection{Finite Automata-Based Pattern Matching}

\paragraph{Pattern Tokenization}
Pattern expressions are split into tokens and parsed recursively. The parser
supports anchors, grouping, quantifiers, and nested patterns. It represents
the quantifiers \texttt{*},
\texttt{+}, \texttt{?}, and \texttt{\{i,j\}} with minimum and maximum counts
together with a greedy or reluctant preference. A trailing \texttt{?}
makes a quantifier reluctant. This gives the builder one internal
representation for all quantifiers.

\paragraph{NFA Construction}
We use Thompson's construction to convert pattern tokens into an NFA.
The automaton stores transitions, variable bindings, anchors, and metadata
for additional pattern features. Quantifiers (\texttt{*}, \texttt{+},
\texttt{?}, \texttt{\{i,j\}}) are mapped to sub-automata. Each transition
that consumes a row is guarded by the \texttt{DEFINE} predicate of its
variable~\cite{Thompson1968,HopcroftUllman}. Fig.~\ref{fig:meth-nfa} shows a simplified NFA for
\texttt{A+ B?}. State $q_1$ is reached after one or more \texttt{A} rows and is
accepting because \texttt{B} is optional. An $\varepsilon$-transition leads
to the connector state $r$. Consuming one \texttt{B} row then reaches the
second accepting state $q_2$. When several continuations are possible, transition
metadata preserves their pattern order. Greedy quantifiers prefer a longer
valid match, reluctant quantifiers prefer a shorter one, and alternation follows
declaration order. The builder also handles grouping, alternation, anchors,
and exclusions. Rows inside an exclusion block still take part in matching,
but are left out of the output. \texttt{PERMUTE} over $m$ variables represents all
$m!$ orders.

\paragraph{DFA Construction and Optimization}
The NFA is converted into a DFA using subset construction. After construction,
unreachable states are removed and transitions are normalized; this is a
conservative reduction rather than full DFA minimization. The engine keeps
pattern metadata and evaluates predicates during matching. A DFA transition
alone does not resolve every SQL preference or state-dependent condition
\cite{HopcroftUllman}.

\paragraph{Construction limits} Subset construction has exponential worst-case
cost, so the compiler uses explicit limits. \texttt{PERMUTE} is rejected
above eight variables or an estimated 50,000 branches. Both limits reject
nine variables: $8! = 40{,}320$ is below the branch limit, while
$9! = 362{,}880$ exceeds it. DFA construction has a maximum of 50,000
states and an iteration limit. The state limit may be lower when less
memory is available. Reaching any limit raises a compilation error. The
engine never executes or caches a partial automaton, and none of the
evaluated patterns reached these limits.

\subsection{Execution Engine and Performance Optimization}

\paragraph{Execution engine}
The matching engine processes DataFrame partitions sequentially, selecting an
eligible compiled plan or general evaluation, with specialized handling for
anchors, skip modes, and edge cases. The executor coordinates parsing,
automaton construction, matching, and result formatting.

A match never crosses a partition boundary, so the DataFrame is first split on
the \texttt{PARTITION BY} columns, or treated as one partition when there are
none. The engine then checks whether each partition already follows the
complete \texttt{ORDER BY} specification and sorts it if needed. A stable
sort keeps rows with equal keys in their original DataFrame order. The matcher
scans the ordered rows, tests the possible transitions at each position, and
follows the pattern's preferences. Each completed match records its start,
end, variable assignments, and excluded rows. These records are used for skip
handling and measure evaluation.

Some predicates depend on the match built so far, for example when accepting a
row changes a running average used by a later condition. When these dependencies
require exact search, the engine uses preference-ordered depth-first search
with backtracking. The search is
iterative, so Python's recursion depth does not limit the match length, and a
state budget and a search budget limit the explored states and steps.
Reaching either limit raises an error instead of returning a partial or
different match.

After a match, the engine resumes according to the four
\texttt{AFTER MATCH SKIP} modes: past the last row (the default), to the next
row, or to the first or last row of a named variable. Empty matches always
advance by one row, and a target that is absent from the match or points back
to its start raises an error, which prevents a silent loop.
\texttt{ONE ROW PER MATCH} returns one summary row per match, while
\texttt{ALL ROWS PER MATCH} returns every visible matched row and supports
\texttt{SHOW EMPTY MATCHES}, \texttt{OMIT EMPTY MATCHES}, and
\texttt{WITH UNMATCHED ROWS}. Measures are compiled once for common navigation
and aggregate forms. Navigation checks row bounds and returns \texttt{NULL}
when a reference is out of range. \texttt{MATCH\_NUMBER()} numbers matches
within each partition. Eligible paths build the output columns directly
before creating the result DataFrame.

The ordered-input check takes $O(n)$ time for a partition of $n$ rows.

use another eligible path. A supported running-average predicate uses a
separate incremental plan, which updates the aggregate as the matched prefix
grows and reverses updates during backtracking. This avoids repeated
full-prefix aggregation for that form; it does not make all state-dependent
conditions vectorizable.

them, lazy row access, output projection, and separate cache, construction,
and search budgets. The bounded least-recently-used (LRU) cache removes old

uncached. Reaching a DFA construction or exact-search limit instead raises
an error. These techniques reduce temporary memory use, but the engine still
keeps the input and result in memory. Some paths also keep materialized rows
or whole-column arrays. The budgets do not limit total process memory.

\section{Experimental Evaluation}

\subsection{Evaluation Methodology}

\subsubsection{Evaluation Criteria and Metrics}

We evaluate correctness, feature coverage, code size, execution time,
throughput, memory use, and scalability. A \emph{cell} is one pattern--size
combination for one system.

\texttt{Correctness}: we compare normalized output rows and values with
Trino~473 and Oracle~21c EE. Agreement applies to the tested queries and
datasets. It does not establish full SQL conformance or the same output order
for every query.

\texttt{Feature coverage}: each main clause is marked as supported, partly
supported, or unsupported based on the reference tests. These tests cover
\texttt{PERMUTE}, exclusions, quantifiers, navigation functions, and output
modes. A pattern type counts as covered when at least one case returns the
same output as the reference systems~\cite{iso2016,ISO2021,monierashraf2025rowmatch}.

\texttt{Developer effort (code size)}: we count lines of detection logic in
three worked examples. We exclude blank lines, comments, imports, setup, and
printing. The thesis records 14 versus 23 lines for dip detection, 14 versus
25 for rising-price detection, and 16 versus 31 for V-shaped recovery (SQL
versus hand-written Pandas). This compares code size; it is not a user study
of productivity.

\texttt{Execution time}: time is measured at the client and includes query
execution and creating or transferring the result. Data loading is excluded.
Each main-benchmark cell uses five warm-up runs and twenty measured runs.
Outliers are removed using the 1.5$\times$ interquartile range (IQR) rule.
The IQR is the difference between the 25th and 75th percentiles. Values more
than 1.5 IQR below the lower percentile or above the upper percentile are
removed.

\texttt{Throughput}: for each run, we divide the input row count by execution
time. We filter and average these rates separately, so the reported value is
the mean of the run rates.

\texttt{Query memory}: this is the incremental peak, or the extra memory
used during a query. We subtract a baseline averaged over a five-second idle
period before the query from the highest sample taken during the query.
Samples are read every 50\,ms from the Linux control-group (cgroup v2)
counter for the engine process or database container.

\texttt{Footprint}: this is the absolute peak from the same counter. It
includes memory already in use, such as the input DataFrame, the Trino Java
Virtual Machine (JVM) heap, or the Oracle System Global Area (SGA). Memory is
reported in MiB ($2^{20}$ bytes) and GiB ($2^{30}$ bytes). Each cell gives the
mean of filtered per-run sampled peaks. A maximum across cells is the largest
of these means, not the largest allocation in any single run.

\texttt{Scalability}: we measure how time and memory use change as input size
increases, up to 227,899,533 rows. A least-squares linear fit summarizes time
growth. Its $R^2$ value shows how much of the measured variation the fitted
line explains.

\subsubsection{Environment and Configuration}

The experiments used Ubuntu~24.04.4 LTS on an Intel Core i7-11800H
(8 cores, 16 threads, 2.30\,GHz) with 64\,GB DDR4 RAM at 3200\,MHz.
Trino~473 and Oracle~21c EE ran in Docker containers on the host daemon.
The recorded runtime environment included Java~11.0.25 LTS,
Python~3.12.7, \texttt{pandas}~2.3.3, \texttt{numpy}~2.1.3, and
\texttt{antlr4-python3-runtime}~4.13.2. ANTLR4 handles SQL parsing,
Pandas manages the input and output tables, and custom AST and automata
modules implement row-pattern execution.

In the main benchmark, every system had the same limits: one CPU core and 32\,GB of
memory, enforced through Linux control groups. The engine had its own group,
and each database container mapped to a host control group. The same type of
counter was therefore used for all three systems.

In the main benchmark, Trino used its in-memory connector. In the large-scale
test, the memory limit was 58\,GB; Trino used a disk-backed Hive/Parquet table,
and Oracle used a native table loaded by direct path. Systems ran one at a
time, and the database containers were restarted before each dataset size.
The main benchmark used five warm-up runs and twenty measured runs per cell.
The large-scale test used two warm-up runs, five measured runs, and a
600-second limit per query. All systems used the same host, logical queries,
input rows, CPU allocation, and outer memory limits. Database configurations
were left at their defaults. Appendix~\ref{app:provenance} gives the full
protocols.

\subsection{Complexity Analysis}

\paragraph{Theoretical bounds}
Let $n$ be the input row count, $m$ the expanded pattern size, $d$ the number
of \texttt{DEFINE} variables, $k$ the number of matches, and $\ell$ the mean
number of output rows per match. Bounded repetitions count their expanded
fragments in $m$; $\ell=1$ under \texttt{ONE ROW PER MATCH}.

Pattern compilation is independent of the input rows. Thompson construction
produces an NFA with $O(m)$ states and uses $O(m)$ space for its graph.
Subset construction can produce
$O(2^m)$ DFA states in the worst case. \texttt{PERMUTE} over $v$ variables
expands to $v!$ orders. Compilation has explicit limits and a bounded cache;
these costs are constant with respect to $n$ for a fixed query, but they are
not necessarily small for arbitrary patterns. Reaching a construction limit
raises an error; an incomplete DFA is not executed or cached.

Consider a fixed pattern that supports the compiled row-local path and uses
the default skip policy. On this path,
predicate preparation costs $O(nd)$ and matching with output construction costs
$O(n+k\ell)$. Sorting costs $\sum_h O(n_h\log n_h)$ over partitions of $n_h$
rows, bounded by $O(n\log n)$, and an $O(n)$ order check avoids sorting already
ordered input. With fixed $d$ and non-overlapping, nonempty matches,
$k\ell=O(n)$: the ordered benchmark path is therefore $\Theta(n)$, and the
unordered case is $O(n\log n)$. Extra memory on this path is
$O(nd+n+k\ell)$, or $O(n)$ for the fixed benchmark queries.

These bounds do not cover every supported expression, output mode, or skip
policy. General evaluation and preference-ordered exact search can depend on
both data size and pattern ambiguity, and search can be exponential in the
worst case. The search has a work limit and raises an error when that limit is reached.
Compiler limits do not remove this dependence on the input data. The evaluated running-average form has a separate incremental plan. Its
linear cost does not apply to all state-dependent predicates.

\paragraph{Empirical evidence}
The main benchmark's per-family linear fits give $R^2=0.9904$--$0.9997$.
The shuffled-input case measures the additional sorting cost; over 100K--2.22M
rows, $\log_2 n$ changes only from about 17 to 21, so the observed curve can
still appear nearly straight. A high $R^2$ describes the measured range and
does not prove a general complexity bound.

\subsubsection{Sensitivity and Boundary Analysis}
\label{sec:sensitivity}

The main benchmark uses ordered input and predicates that depend only on the
current row. We test two changes to these conditions. First, we shuffle each
input using a fixed procedure while keeping the same logical ordering key.
The engine must then sort the rows, with an $O(n\log n)$ cost. All 90 cells
complete with the same match counts (Table~\ref{tab:ordering_by_size}). The
mean slowdown is 1.43$\times$ for the engine, 1.04$\times$ for Oracle, and
1.11$\times$ for Trino. At 2,222,742 rows, mean engine time increases from
0.43 to 0.63 seconds. With shuffled input, it remains 4.5$\times$ faster
than Oracle and 8.8$\times$ faster than Trino at full size. The corresponding
ordered-input ratios are 6.2$\times$ and 11.2$\times$. The engine therefore
keeps its measured lead when sorting is required.

Second, we change the \texttt{simple\_sequence} query's \texttt{DEFINE} to
\texttt{B AS category = 'B' AND price > AVG(A.price)}. The running average
depends on the match built so far, so the condition cannot be evaluated
entirely with row-local Boolean masks. An earlier recorded implementation
used the general exact evaluator and took 64.41 seconds at full size. It was
the slowest system at every size because it repeatedly calculated
\texttt{AVG(A.price)} from the matched rows. The current engine updates this
average incrementally. It takes 1.28 seconds at full size, about 50$\times$
faster than that earlier run, compared with 2.32 seconds for Oracle and
8.67 for Trino. Across the six sizes, it is 1.2--1.8$\times$ faster than
Oracle and 5.0--15.9$\times$ faster than Trino. All three return identical
output, with 181,147 matches at full size (Table~\ref{tab:worstcase_coverage}).
The database means in this test use only two measured runs per size.

This test covers one supported aggregate form. Prices in category A are at most
\pounds10, and prices in category B exceed \pounds10, so every B row after a nonempty A
run already satisfies the average comparison. The test therefore measures
the cost of handling the aggregate; it does not test difficult cases where
the average causes a candidate row to be rejected. Other state-dependent or
ambiguous cases may need exact search when a faster supported plan does not
apply. Exact search can be exponential and raises an error when its work
limit is reached.

Several design choices help explain the observed performance. The engine
works directly on a DataFrame already in memory, so it does not need a
database client protocol or result transfer from a separate server. Supported
predicates become column operations and integer comparisons, reducing
repeated Python expression evaluation. Ordered input also avoids sorting.
These are possible reasons for the measured differences; the experiment
does not separate their individual costs from database planning and other
system overheads.

All optimizations were enabled, with each used only when its conditions were
met. Differential tests show agreement with general evaluation in the covered
cases, but no ablation study measures the separate effect of each optimization.
The sorting test shows that the engine keeps its measured lead when a sort is
required. The aggregate test supports the incremental plan for one running-average
form. As discussed in Section~\ref{sec:sensitivity}, its price bands make
the aggregate comparison true for every eligible B row, so this result does
not describe difficult state-dependent searches in general.

The main memory trade-off is higher incremental query memory. Whole-column
working arrays reduce repeated computation but need additional RAM. The engine's
largest cell mean is 189.05 MiB, the highest of the three, while its total
footprint is the lowest in the main benchmark. These measures answer
different questions: query memory is growth above the pre-query baseline,
whereas the footprint includes memory already held by the engine process or
database container. At the largest scale-test size, the engine's mean
footprint exceeds Oracle's. Faster execution therefore does not imply the
lowest memory use at every scale.

The results address the main research objectives: declarative pattern
recognition runs directly on a DataFrame, the tested outputs agree with two
SQL reference engines, and the engine completes the evaluated corpus up to
227.9 million rows. Execution time is close to linear in the tested range,
while growing memory use makes available RAM a practical boundary. The
worked examples also show how one query can replace procedural matching
logic; they do not measure developer productivity.

These findings apply to one workstation, single-partition timed queries,
five pattern families, and the recorded system configurations. The worked
examples test partitioning, but the benchmarks do not measure its performance.
Systems ran one at a time, and the scale study uses different storage models
for the three systems. Other hardware, predicates, patterns, or database
settings may change the measured differences. The results therefore support
the proposed engine for the evaluated workload rather than a general ranking
of SQL engines.

\section{Conclusions, Limitations and Future Work}

\paragraph{Conclusions}

We presented an in-process engine for an evaluated R010-style subset of
SQL:2016 \texttt{MATCH\_RECOGNIZE} over Pandas DataFrames. It parses SQL, checks the supported semantics, compiles patterns into
automata, and returns a DataFrame. Execution plans have explicit conditions
and limits. On Amazon UK Products, all 30 pattern--size combinations
returned normalized results identical to Trino~473 and Oracle~21c EE. The mean
cell time was 0.17 seconds for the proposed engine, 1.04 for Oracle, and 1.98
for Trino. The separate Amazon Reviews study completed all five pattern
families up to 227,899,533 rows. The worked examples also used fewer lines of
detection logic in SQL than in the corresponding Pandas functions.

\paragraph{Limitations}

The engine implements a supported subset rather than full SQL:2016
conformance. The window form (R020), conditional and subquery ordering keys,
arbitrary user-defined aggregates, and general relational query planning are
outside the evaluated scope. Nested or unbounded quantifiers can increase
automaton size, and \texttt{PERMUTE} expands factorially; compilation limits
can therefore reject large patterns. State-dependent or ambiguous cases may
require exact search, which has no general linear bound and raises an error
when its search budget is exhausted.

The input DataFrame and result must stay in memory. At the largest
scalability size, the engine's four-family mean footprint exceeds Oracle's,
so lower execution time does not always mean lower memory use. Results come
from one workstation, one CPU core, single-partition queries, five timed
pattern families, and default database configurations. Storage representations
also differ in the scale study, and loading time is excluded. All optimizations were measured together; no ablation study measured their
separate effects.

\paragraph{Future Work}

Future work includes out-of-core execution, so the input would not need to
fit entirely in RAM, and support for columnar backends such as Polars or
Apache Arrow. Stronger state pruning, DFA minimization, and faster handling
of state-dependent predicates could reduce execution and compilation costs.
Independent partitions could run in separate workers while keeping a fixed
result order. Further work should also extend the supported SQL clauses and
measure expressions. Further experiments should test wider tables, more partitions,
other query structures, and tuned databases. An ablation study should also
measure the separate effect of each optimization. Integration with query
optimizers could support improvements at the plan level.

\subsection{Measurement Provenance and Reproducibility}
\label{app:provenance}

Systems ran one at a time, so they did not compete for the same CPU core
or memory. The engine results were updated using revision \texttt{f8b052d}.
Trino and Oracle values were kept from earlier experiments that followed the
same protocol. The thesis reports 709 passing cases for the recorded
regression snapshot; this is the historical evaluation count.

\paragraph{Benchmark protocols}
The evaluation used four fixed protocols:
\begin{itemize}
  \item \textbf{Cross-system matrix.} One CPU core, an outer 32\,GB memory
    limit, five warm-up runs, and twenty measured runs on ordered input. The
    matrix contains five patterns and six sizes (100K--2,222,742 rows), giving
    30 cells per system; all 90 cells completed.
  \item \textbf{Stress test.} One CPU core, a 58\,GB memory limit, two warm-up
    runs, five measured runs, and a 600\,s limit per query, over five patterns
    and seven sizes (5M--227,899,533 rows). The proposed engine and Oracle
    completed 35 of 35 cells; Trino completed 33 of 35, because
    \texttt{complex\_nested} reached the time limit at 160M and 227,899,533 rows.
  \item \textbf{Ordering test.} The matrix protocol was repeated after a
    deterministic shuffle, which removes physical pre-ordering while keeping
    the same logical \texttt{ORDER BY} key. All 90 shuffled cells completed.
  \item \textbf{State-dependent test.} One CPU core and a 32\,GB memory limit,
    with ordered input and \texttt{B AS category='B' AND price > AVG(A.price)}.
    The proposed engine used five warm-up runs and twenty measured runs per
    size; the retained Trino and Oracle values contain two measured runs per
    size, so their means are useful for comparison but provide less evidence
    about variation. All 18 cells completed.
\end{itemize}

Memory was sampled every 50\,ms from \texttt{memory.current}, the total that
version~2 of the Linux control-group (cgroup) interface reports for a group of
processes. The incremental peak subtracts a five-second pre-query baseline.
For the proposed engine the absolute peak covers its process; for Trino and
Oracle it covers the full database container. Timing includes query execution
and result construction or retrieval, while data generation and loading are
excluded. Memory values use MiB and GiB throughout; the thesis source plots
retain their original MB/GB axis labels.

\paragraph{Measurement exclusions}
No complete benchmark cell was omitted. The 1.5$\times$ IQR rule could remove
individual samples from a cell, and the number removed was retained with the
measurements. The protocol allows a whole cell to be rejected only with recorded evidence
of an invalid run, such as a wrong revision, incorrect resource
limits, host contention, sampler failure, process failure, or incomplete
output.

\subsection{Step-by-Step Execution Analysis}\label{Step-by-Step}

The following examples find three consecutive purchases with decreasing
prices within each customer's ordered history. Listing~\ref{lst:UDF-match-recognize}
implements the \texttt{A B C} pattern procedurally in Pandas and resumes after
the last row of each match.

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize,language=Python,
                   caption={Procedural Pandas baseline for consecutive price declines},
                   label={lst:UDF-match-recognize},
                   frame=single]
import pandas as pd

def detect_dip(df, cust_col="customer_id",
               date_col="order_date", price_col="price"):
    g = df.copy()
    g[date_col] = pd.to_datetime(g[date_col])
    g = g.sort_values([cust_col, date_col]).reset_index(drop=True)
    rows = []
    for cust, grp in g.groupby(cust_col, sort=False):
        grp = grp.reset_index(drop=True)
        i = 0
        while i + 2 < len(grp):
            a, b, c = (grp.loc[i, price_col], grp.loc[i + 1, price_col],
                       grp.loc[i + 2, price_col])
            if b < a and c < b:
                rows.append({
                    "customer_id": cust,
                    "start_date": grp.loc[i, date_col].date(),
                    "end_date": grp.loc[i + 2, date_col].date(),
                    "bottom_price": c,
                })
                i += 3  # AFTER MATCH SKIP PAST LAST ROW
            else:
                i += 1
    return pd.DataFrame(rows)

result_df = detect_dip(df)
print(result_df)
\end{lstlisting}

Listing~\ref{lst:basic-match-recognize} expresses the same task using the
proposed engine. Its omitted skip clause defaults to
\texttt{AFTER MATCH SKIP PAST LAST ROW}, matching the policy in the Pandas
function. Both examples return the customer's identifier, the first and last
purchase dates, and the final price.

\begin{lstlisting}[language=Python,
                   caption={Using \texttt{MATCH\_RECOGNIZE}},
                   label={lst:basic-match-recognize},
                   frame=single]
import pandas as pd
from src.executor.match_recognize import match_recognize
df['order_date'] = pd.to_datetime(df['order_date'])
# Define the MATCH_RECOGNIZE query
query = """
SELECT customer_id, start_date, end_date, bottom_price
FROM orders
MATCH_RECOGNIZE (
  PARTITION BY customer_id
  ORDER BY order_date
  MEASURES
    A.order_date AS start_date,
    C.order_date AS end_date,
    C.price      AS bottom_price
  PATTERN (A B C)
  DEFINE
    B AS B.price < A.price,
    C AS C.price < B.price
);
"""
# Execute and print results
output_df = match_recognize(query, df)
print(output_df)
\end{lstlisting}

This walkthrough applies Listing~\ref{lst:basic-match-recognize} to the eight
orders in Table~\ref{tab:orders}. Positions within a sorted customer partition
are zero-based and differ from positions in the original interleaved table.

\begin{enumerate}
  \item \textbf{Parse and validate the query.} The parser extracts
    \texttt{PARTITION BY customer\_id}, \texttt{ORDER BY order\_date},
    \texttt{PATTERN (A B C)}, the two price comparisons, and the three
    measures. A has no explicit \texttt{DEFINE} predicate and is therefore
    implicitly true. The pattern requires three consecutive rows within the
    ordered partition.

  \item \textbf{Partition and order.} For \texttt{cust\_1}, the prices are $[100,200,100,50,100]$. Their original positions are
    $[0,1,3,5,6]$. The \texttt{cust\_2} partition has prices $[8,4,6]$,
    at original positions $[2,4,7]$. Both are already in date order.

  \item \textbf{Try the first start in \texttt{cust\_1}.} At local
    position~0, A has price~100. The next row has price~200, so
    $B.price<A.price$ fails. The matcher cannot skip this row and search
    farther ahead for B in the consecutive pattern \texttt{A B C}.

  \item \textbf{Find the successful match.} Starting at local position~1,
    the assignments are A~=~200, B~=~100, and C~=~50. Both comparisons hold.
    The local positions are $(1,2,3)$, corresponding to original input
    positions $(1,3,5)$ and dates May~12, May~14, and May~16,~2020.

  \item \textbf{Apply the skip policy.} The default
    \texttt{AFTER MATCH SKIP PAST LAST ROW} resumes at local position~4
    (original position~6). Only one row remains, so no further complete
    match is possible in this partition.

  \item \textbf{Check \texttt{cust\_2}.} The only complete three-row
    candidate has prices $(8,4,6)$. B satisfies $4<8$, but C fails
    $6<4$. Later starts have too few rows for a complete match.

  \item \textbf{Evaluate measures.} With \texttt{grp} denoting the
    date-ordered \texttt{cust\_1} partition, A is \texttt{grp.iloc[1]}
    and C is \texttt{grp.iloc[3]}. The measures are therefore
    \texttt{start\_date}=2020-05-12, \texttt{end\_date}=2020-05-16,
    and \texttt{bottom\_price}=50. These local indices must not be applied
    to the original interleaved DataFrame.

  \item \textbf{Materialize the output.} One result row is returned:
\end{enumerate}

\begin{center}
\small
\begin{tabular}{l l l r}
\toprule
\textbf{customer\_id} & \textbf{start\_date} & \textbf{end\_date} & \textbf{bottom\_price} \\
\midrule
\texttt{cust\_1} & 2020-05-12 & 2020-05-16 & 50 \\
\bottomrule
\end{tabular}
\end{center}

The match describes three consecutive purchases with declining prices for
\texttt{cust\_1}; it does not imply that all of this customer's purchases
follow a declining trend.
