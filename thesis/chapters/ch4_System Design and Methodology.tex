\chapter{System Design and Methodology}
\label{chap:methodology}

This chapter describes how the engine turns a \texttt{MATCH\_RECOGNIZE}
query into something it can run directly on a
\texttt{pandas} DataFrame~\cite{monierashraf2025rowmatch}, and the
design decisions behind that pipeline.  It focuses on the front
end---the stages that take a query from raw text to a validated,
executable plan---while preserving the supported SQL:2016 row-pattern
semantics~\cite{iso2016}.  Chapter~\ref{chap:implementation} continues
from there into automata compilation, execution, and optimization.

% ----------------------------------------------------------------
\section{Architecture Overview}
\label{sec:meth-overview}
% ----------------------------------------------------------------

The engine takes two inputs---the query string and a \texttt{pandas}
DataFrame---and returns a result DataFrame.  Between them it is
organized as five stages, each producing a well-defined
artifact that the next stage consumes
(Figure~\ref{fig:system-architecture}).  \emph{Parsing} turns the SQL
text into an abstract syntax tree (AST) that captures both the outer
\texttt{SELECT}/\texttt{FROM} and the \texttt{MATCH\_RECOGNIZE}
sub-clauses.  \emph{Semantic validation} checks that the query is
actually meaningful---variables, predicates, output and skip
modes---before any work is committed.  \emph{Logical-plan
construction} flattens the validated AST into a single canonical
structure.  \emph{Pattern compilation} turns the pattern into a finite
automaton, and \emph{execution} runs that automaton over the ordered
data and returns a DataFrame.

The stages are a real division of work, not just a way to describe it.
Each one has a single job and a single output.  A failure therefore has
one place to come from, and each stage can be tested on its own
artifact.  The order also puts the cheap work first: the query is
checked before the automaton is built, and the automaton is built before
a single row is read.

The \emph{parser} recognizes the
query's parts---partitioning, ordering, the pattern, its conditions,
and the output measures---and organizes them into the AST, which the
semantic validator and logical planner then check and normalise before
anything is compiled.  The \emph{automata compiler} converts the pattern
into a non-deterministic finite automaton (NFA) and then a
deterministic one (DFA), so that repetition, alternation, and
sequencing are all handled
uniformly~\cite{georgiou2025streaming}.  The \emph{execution engine}
partitions and orders the DataFrame, scans it with the compiled
automaton under the configured skip mode, computes each match's
measures, and assembles a result DataFrame that mirrors ordinary SQL
output.  The rest of this chapter covers the first three stages;
Sections~\ref{sec:meth-compiler}--\ref{sec:meth-logical} take them in
turn.

\section{SQL Parsing}
\label{sec:meth-compiler}
% ----------------------------------------------------------------

A \texttt{MATCH\_RECOGNIZE} query mixes ordinary SQL with an extended
row-pattern sub-language: eight sub-clauses, and, inside
\texttt{PATTERN}, its own grammar of quantifiers, alternation,
grouping, anchors, exclusions, and \texttt{PERMUTE}.  The parser must
understand both.  Listing~\ref{lst:mr-full-syntax} summarises the
syntax the engine supports.

\begin{lstlisting}[
    language   = {},
    caption    = {Syntax of a \texttt{MATCH\_RECOGNIZE} query},
    label      = {lst:mr-full-syntax},
    basicstyle = \ttfamily\footnotesize
]
SELECT <expression> [, ...]
FROM   <table>
MATCH_RECOGNIZE (
  [ PARTITION BY <column> [, ...] ]
  [ ORDER BY <column> [ASC|DESC] [, ...] ]
  [ MEASURES <expression> AS <alias> [, ...] ]
  [ ONE ROW PER MATCH
  | ALL ROWS PER MATCH
    [ SHOW EMPTY MATCHES
    | OMIT EMPTY MATCHES
    | WITH UNMATCHED ROWS ] ]
  [ AFTER MATCH SKIP
    { PAST LAST ROW
    | TO NEXT ROW
    | TO FIRST <variable>
    | TO LAST  <variable> } ]
  PATTERN ( <row_pattern> )
  [ SUBSET <subset_name> = ( <variable> [, ...] ) [, ...] ]
  [ DEFINE <variable> AS <condition> [, ...] ]
) [ AS <alias> ]
<rest>;
\end{lstlisting}

The engine targets one \texttt{MATCH\_RECOGNIZE} clause inside a
top-level \texttt{SELECT} with an optional outer \texttt{ORDER~BY};
the \texttt{DEFINE} clause is optional, and any pattern variable used
without a predicate is treated as always-true.  Full CTE rewriting,
set-operation planning, and general nested subqueries lie outside this
path, which is sufficient for the \texttt{FROM}-clause row-pattern
cases evaluated in this thesis.

\paragraph{Choosing a parser.}
The requirement is a typed tree for both languages at once.  None of the
Python SQL libraries surveyed when the parser was chosen met it.
\texttt{sqlparse}~\cite{sqlparse_tool}
produces only a shallow token stream;
\texttt{sqlglot}~\cite{sqlglot_tool} and
\texttt{mo\_sql\_parsing}~\cite{mo_sql_parsing_tool} expose a typed AST
but omit constructs such as exclusions, anchors, \texttt{PERMUTE}, and
bounded quantifiers; and \texttt{pglast}~\cite{pglast_tool} cannot
parse \texttt{MATCH\_RECOGNIZE} at all.  Rather than extend one of
these, the engine reuses the community ANTLR4 grammar for the Trino
SQL dialect~\cite{antlr_trino_sql,Parr2013}, whose \texttt{.g4} files
already contain a \texttt{pattern\-Recognition} rule covering all eight
sub-clauses.  ANTLR4 generates the lexer, parser, and traversal
scaffolding directly from that grammar, so no grammar changes were
needed.

Two properties of the tool matter for a grammar this size.  The first is
lookahead.  Most parser generators commit to a rule after a fixed number
of tokens, and a grammar needing one more must be reshaped by hand.
ANTLR4 instead reads as far ahead as the input requires.  Its authors
call this \emph{adaptive} $LL(*)$, written
\emph{ALL(*)}~\cite{parr2014adaptive}.  So where ordinary SQL and a
row-pattern construct could be read either way, the input decides.  The second is
\emph{left recursion}: rules that refer to themselves on the left.  The
grammar writes conjunction as \texttt{booleanExpression AND
booleanExpression}, the shape a classical top-down parser loops forever
on.  ANTLR4 rewrites it internally, so SQL's expression rules keep the
form the standard gives them.

Syntax errors go through a custom \emph{error listener} rather than
ANTLR's console default, so each carries the exact line, column, and
source snippet.  A hand-written recursive-descent parser or a set of
regular expressions was rejected: the former is hard to maintain across
SQL's hundreds of productions, and the latter cannot model recursive
structures such as nested grouping.

\paragraph{From parse tree to a typed AST.}
ANTLR4's raw parse tree is a \emph{concrete syntax tree}: it keeps every
token the grammar matched, keywords and punctuation included, most of
which execution does not need.  Lowering it to an abstract one follows
the \emph{Visitor} pattern~\cite{robson2022designpatterns}.  ANTLR4
emits a visitor base class from the grammar, and a pair of cooperating
subclasses---one for the outer query, one for the
\texttt{MATCH\_RECOGNIZE} clause---walk the tree and produce a compact,
typed AST: a root node holding the outer \texttt{SELECT}/\texttt{FROM}
and a single
\texttt{MatchRecognizeClause}, with every sub-clause represented as its
own typed dataclass (partitioning, ordering, measures, rows-per-match,
skip mode, pattern, subset, and define).  Later stages then dispatch
on node type instead of re-inspecting raw strings.

One exception is deliberate.  The predicates in \texttt{DEFINE} and the
expressions in \texttt{MEASURES} stay as text and are interpreted on
demand.  That keeps the grammar small.  The price is that those strings
must still be evaluated safely later.

\paragraph{Safe expression evaluation.}
Those strings come from the user, so the engine never runs them as
Python code.  It reads each one into a small tree of operations and
walks that tree itself.  The walk follows an \emph{allowlist}: an
operation is evaluated only if the engine has a handler for it.
Anything not on the list cannot run at all.  Safety comes from how the
evaluator is built, not from remembering to block things one at a time.

The list holds what the row-pattern language needs: comparisons,
arithmetic and unary operators, and boolean connectives; literals, and
the tuple and list forms \texttt{IN} uses; conditional expressions for
\texttt{CASE~WHEN}; qualified references such as \texttt{A.price}; and a
fixed set of calls---the navigation functions \texttt{PREV},
\texttt{NEXT}, \texttt{FIRST} and \texttt{LAST}, \texttt{CLASSIFIER},
and the supported aggregates.  Imports, assignments, and any reach into
built-ins, the file system, or the network are not on it.  An expression
therefore sees one thing: the \emph{row context}, holding the current
row and the pattern-variable bindings.

The parser is exercised by a dedicated test layer.  It includes
adversarial inputs---undefined variables, prohibited function forms,
invalid skip targets, and incompatible output-mode combinations---and
end-to-end scenarios adapted from Trino's row-pattern test suite.  Two
limits follow from the design.  SQL features outside the row-pattern
subset, recursive CTEs inside predicate subqueries for example, are not
on the main execution path.  And because the grammar tracks Trino's
dialect, other vendors' extensions may need small grammar adjustments.

\section{Semantic Validation}
\label{sec:meth-semantic}
% ----------------------------------------------------------------

Parsing proves a query is well formed.  It does not prove the query
means anything.  \texttt{PATTERN (A B)} with \texttt{DEFINE B AS
B.price > Q.price} parses cleanly, but \texttt{Q} is a variable the
pattern never declares, so the condition compares against nothing.

A validation pass therefore runs once the AST is complete, before any
automaton is built.  It does two jobs: it rejects queries that parse but
have no clear meaning in the supported subset, and it fills in the
defaults the later stages depend on.  Running it here is what makes the
error useful.  Nothing has been compiled and no row has been read, so
the message can name the reference it could not resolve and the clauses
it searched.  The checks fall into three groups.

\emph{Every name must refer to something.}  This is ordinary \emph{name
resolution}, with the pattern as its scope.  A condition cannot be
evaluated if the variables it mentions do not exist, so the validator
checks each name in \texttt{DEFINE} and \texttt{MEASURES} against the
variables the \texttt{PATTERN} declares and any \texttt{SUBSET} aliases.
A subset such as \texttt{SUBSET U = (A, B)} lets \texttt{U.price} stand
for the rows matched by either variable, and the alias is replaced by
its members before matching.  A variable used without a \texttt{DEFINE}
still counts, because it is treated as always true.  A name that matches
nothing is rejected, and the message says which one.  Column names are
resolved later, against the DataFrame itself, so a missing
\texttt{PARTITION BY} or \texttt{ORDER BY} column is reported at that
point.

\emph{Calls must be written correctly.}  Each navigation and aggregate
function takes a fixed set of arguments: \texttt{FIRST}, \texttt{LAST},
\texttt{PREV} and \texttt{NEXT} take a value and an optional offset,
\texttt{COUNT\_IF} takes one condition, and \texttt{SUM\_IF} and
\texttt{AVG\_IF} take two.  Checking this here means a badly written
call is caught before anything is compiled, instead of failing later
inside execution where the cause is harder to trace.  Nesting is
allowed, so \texttt{NEXT(PREV(A.price, 1), 1)} passes.  What this check
does not do is decide whether a condition can ever be true.  A condition
that never holds simply returns no rows, which is how the reference
engines behave.

\emph{Settings must work together.}  Some combinations ask for
contradictory output.  An exclusion, written \texttt{\{-\ \ldots\ -\}},
keeps matched rows out of the result, while \texttt{ALL ROWS PER MATCH
WITH UNMATCHED ROWS} asks for every row to appear; one removes what the
other requires, so the standard forbids the pair and the validator
rejects it.  An \texttt{AFTER MATCH SKIP} target is treated the same
way: skipping to a variable only means something if that variable
exists.  One case cannot be settled in advance.  \texttt{AFTER MATCH
SKIP TO FIRST A} on \texttt{PATTERN (A B)} would send the search back to
the row the match began on and find the same match forever, so the
matcher detects it while running and stops with an explicit error.  When
the checks pass, the resolved configuration goes to the planner---the
output mode, the skip mode, and the always-true default for variables
with no condition---and measure semantics are decided during planning
(Section~\ref{sec:meth-logical}).

\section{Logical Plan Construction}
\label{sec:meth-logical}
% ................................................................

The logical plan is the engine's \emph{intermediate representation}: the
one structure every later phase reads.  It is a set of typed attributes
pulled from the \texttt{MatchRecognizeClause} and passed explicitly to
the execution functions (Table~\ref{tab:logical-plan}).  From here on no stage reads
the SQL text again.  That is what the boundary buys: a change to the
query syntax stays in the front end, a change to matching stays in the
back end.

\begin{table}[htbp]
  \centering
  \caption{Principal logical-plan attributes extracted from the
    validated AST}
  \label{tab:logical-plan}
  \begin{tabular}{llp{6.5cm}}
    \toprule
    \textbf{Attribute} & \textbf{Type} & \textbf{Semantics} \\
    \midrule
    \texttt{partition\_by}   & \texttt{List[str]}
      & Columns for DataFrame partitioning; empty means a single
        global partition \\[4pt]
    \texttt{order\_by}       & \texttt{List[str]}
      & Columns for the intra-partition sort order \\[4pt]
    \texttt{pattern\_text}   & \texttt{str}
      & Normalized pattern string forwarded to the tokenizer \\[4pt]
    \texttt{define}          & \texttt{Dict[str, str]}
      & Variable $\to$ predicate; implicit variables get the
        always-true predicate \texttt{"True"} \\[4pt]
    \texttt{subset\_dict}    & \texttt{Dict[str, List[str]]}
      & Subset alias $\to$ constituent variables \\[4pt]
    \texttt{measures}        & \texttt{Dict[str, str]}
      & Measure alias $\to$ expression string \\[4pt]
    \texttt{measure\_semantics} & \texttt{Dict[str, str]}
      & Measure alias $\to$ \texttt{"RUNNING"}/\texttt{"FINAL"}, per
        the rules in Figure~\ref{fig:measure-sem-resolution} \\[4pt]
    \texttt{rows\_per\_match} & \texttt{RowsPerMatch}
      & Output-row multiplicity \\[4pt]
    \texttt{skip\_mode}      & \texttt{SkipMode}
      & After-match skip strategy \\[4pt]
    \texttt{skip\_var}       & \texttt{Optional[str]}
      & Target variable/alias for \textsc{To First}/\textsc{To Last} \\
    \bottomrule
  \end{tabular}
\end{table}

Two normalisations matter.  First, the always-true rule from
Section~\ref{sec:meth-compiler} takes concrete form here: a pattern
variable with no \texttt{DEFINE} gets the literal predicate
\texttt{"True"}, so downstream code treats every variable the same.
Second, each measure
is tagged \textsc{Running} or \textsc{Final}---from an explicit prefix,
or, when none is given, by the fixed precedence in
Figure~\ref{fig:measure-sem-resolution}.  The engine scans the measures
once to see whether any is explicit, then applies the rules top to
bottom: under \texttt{ONE ROW PER MATCH} all are \textsc{Final}; under
\texttt{ALL ROWS PER MATCH}, \texttt{FIRST}/\texttt{PREV}/\texttt{NEXT}
are \textsc{Final} and \texttt{LAST} \textsc{Running}, supported
aggregates default to \textsc{Running}, and anything else to
\textsc{Final}.

\section{Chapter Summary}
\label{sec:meth-summary}
% ----------------------------------------------------------------

This chapter presented the front-end design of the proposed
\texttt{MATCH\_RECOGNIZE} engine: the five-stage architecture, and how
the first three stages---parsing, semantic validation, and logical-plan
construction---turn a user query into a validated logical
representation.  Along the way it explained why an ANTLR4 grammar for
the Trino dialect was reused rather than a new parser written, how
user expressions are evaluated safely, and how output and measure
semantics are resolved.  These stages mark the boundary between
declarative SQL input and the execution machinery.
Chapter~\ref{chap:implementation} takes that up next: automata
compilation, the Pandas execution model, and the optimization
techniques behind the engine's runtime and memory behaviour.
