\chapter{Detailed Benchmark Tables}
\label{app:benchmark-tables}

This appendix presents the detailed benchmark tables used in
Chapter~\ref{chap:evaluation}.  The chapter explains the main results,
while this appendix keeps the full values for verification.  Unless
stated otherwise, the tables use the Amazon UK Products benchmark and
the cross-system protocol below.

\section{Measurement Provenance and Reproducibility}
\label{app:provenance}

All systems ran sequentially, one at a time.  No two systems ran
together, so they never competed for the same CPU core or memory.
Proposed-engine runs were refreshed on revision \texttt{179c286}.  Trino and
Oracle values were retained from protocol-aligned earlier campaigns;
the state-dependent repetition difference is disclosed below.  The
final regression run passed 709 tests.

\paragraph{Benchmark protocols.}
The evaluation used four fixed protocols:

\begin{itemize}
  \item \textbf{Cross-system matrix.} One CPU core, an outer 32\,GB memory
    limit, five warm-up runs, and twenty measured runs.  The input was ordered, and
    the warm-up runs preceded measurement.  The matrix contains five patterns and six
    sizes (100\,K--2\,222\,742 rows), giving 30 cells per system.
    All 90 cells completed.  The 30 proposed-engine cells are from the
    recorded engine campaign.  The 60 database cells are retained results.
  \item \textbf{Stress test.} One CPU core, a 58\,GB memory limit, two warm-up runs,
    and five measured runs.  Each query had a 600\,s limit.  The test
    contains five patterns and seven sizes (5\,M--227\,899\,533 rows).
    The proposed engine and Oracle completed 35 of 35 cells.  Trino
    completed 33 of 35; \texttt{complex\_nested} reached the time
    limit at 160\,M and 227\,899\,533 rows.
  \item \textbf{Ordering test.} The matrix protocol was repeated after
    a deterministic shuffle.  This removed physical pre-ordering while
    keeping the same logical \texttt{ORDER BY} key.  All 90 shuffled
    cells completed.
  \item \textbf{State-dependent test.} One CPU core and a 32\,GB memory limit were
    used with ordered input and
    \texttt{B AS category='B' AND price > AVG(A.price)}.  The proposed
    engine used five warm-up runs and twenty measured runs per size.
    The retained Trino and Oracle reference values contain two
    measured runs per size.  Their means are useful for comparison,
    but provide less evidence about variation.  All 18 cells completed.
\end{itemize}

Memory was sampled from the control group's cgroup~v2 counter every
50\,ms.  The incremental peak subtracts a five-second pre-query
baseline.  Timing includes query execution and result construction or
retrieval.  For the proposed engine, the absolute peak covers its
process.  For Trino and Oracle, it covers the full database container.
Database-native query counters are reported separately where
available.  Data generation and loading are excluded.
The scripts divide byte counters by $1024^2$ and $1024^3$; MB and GB in
the memory tables therefore mean MiB and GiB.

The saved benchmark bundle contains the result tables and provenance
records for the main matrix, ordering, state-dependent, and stress
campaigns.

\paragraph{Measurement exclusions.}
No complete benchmark cell was omitted.  The stated 1.5$\times$ IQR
rule could remove individual samples from a cell.  The number removed
was retained with the measurements.  A complete cell may be rejected
only when there is recorded evidence of an invalid run, such as a
wrong revision, incorrect resource limits, host contention, sampler
failure, process failure, or incomplete output.

\paragraph{Known limitations.}
The engine is single-node and in-memory.  Its practical limit depends
on available RAM, input width, output size, and pattern structure.
The executor selects among compiled row-local predicates, supported
incremental aggregate paths, and general exact search.  The selected
path depends on both the expression and the pattern.  The absence of a
simple column operation does not by itself imply exact search.

\section{Detailed Cross-System Benchmark Matrices}
\label{app:benchmark-matrices}

Chapter~\ref{chap:evaluation}.  Execution time includes result
construction or retrieval.  For each measured run, throughput is input
size divided by that run's time.  Cell throughput is the arithmetic
mean of the retained per-run rates after applying the same
1.5$\times$ IQR rule independently to throughput.  It is not input
size divided by the cell's mean time.  Query memory is the incremental
cgroup peak above the five-second baseline.  Footprint memory is the
absolute cgroup peak.  Time and memory are also filtered independently
and reported as means of the retained samples from twenty measured
runs.
